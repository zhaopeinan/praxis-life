# 第 13 讲 AI 结对编程的纪律：系统落地设计

> 来源：`../design_principle/第13讲_AI结对编程的纪律.pdf`
> 落地度：★★★★☆（高） ｜ 依赖：无强依赖，与第 16 讲互喂 ｜ 主体分期：P0
> 主产物：表 `13 接口契约`（一行 = 一个待实现函数，含四要素契约与三个自检）+ 表 `13 AI 代码审查`（一行 = 一遍审查）+ 表 `13 上下文包`（一行 = 一份给 AI 的上下文）+ 表 `13 步长记录`（轻量，把失控信号变成可统计的列）

## 1. 本讲方法要点

1. **契约先行**。AI 生成代码的质量上限取决于你描述意图的精确度；模糊的指令交给 AI，等于把设计权拱手让出。**设计恰恰是最不该让出的部分**。
2. **一份合格的契约有四要素**：输入（参数名、类型、取值范围、单位）、输出（返回值结构、类型、边界情形下的形态）、前置条件（调用前必须满足什么）、后置条件与异常（保证什么成立、失败时抛什么）。
3. **契约写在函数签名与文档字符串里，不写在聊天记录里**——这样它既是给 AI 的规格说明，也是日后审查与测试的基准。
4. **契约的三个自检**：一个不了解你项目的同事，能否仅凭契约写出实现？能否仅凭契约写出测试？契约里有没有「合理处理」「适当返回」这类无法验收的措辞？三问有一问答不上来，契约就还没写完。
5. **小步快跑**：单次生成不超过 50 行、只实现一个函数或只改一处逻辑。理由是三条成本——错误定位成本（50 行里找错是分钟级，300 行里找错是小时级）、审查可行性（人能认真读完的代码量有限）、回退代价（小步错一步退一格，大跨步错要退一片）。
6. **每步生成之后立即验证，验证分三档由轻到重**：能加载（模块能导入、无语法与导入错误）→ 能跑通（用手工构造的小样例走一遍主路径）→ 能通过（对应单元测试全部变绿）。**未经验证的代码不允许堆积**。
7. **步长失控的三个信号**：单次生成后你需要「读一会儿」而不是「扫一眼」才能理解；验证失败的次数开始超过一次；你开始用「先合并了再说」来安抚自己。出现任何一个，下次请求把任务再切小一半。
8. **三遍审查，关注点互不重叠**：第一遍语法能跑（机器判）、第二遍逻辑正确（对照契约判：分支符合契约吗、边界处理了吗、异常被吞了吗；重点看 AI 最易错处——下标偏移、空集合、时区与单位、隐式类型转换）、第三遍风格一致（对照仓库判：命名惯例、文件摆放、有没有引入项目里从未用过的依赖与写法）。
9. **上下文工程追求「最小但充分」**，三样东西：仓库结构摘要（目录树 + 一句话职责）、相关接口签名（本次改动会直接调用的签名与契约，不是整个文件）、测试样例（一两个输入输出对，既是格式说明也是验收标准）。**上下文有保鲜期**，过期的上下文比没有上下文更糟——AI 会一本正经地遵循你已经放弃的旧设计。
10. **提交信息中标注哪些代码由 AI 生成**（操作清单第 5 条）。

| 生成行数与提交 diff 对账 | 从 git diff 统计行数回填 `AI 生成行数` | 脚本 / MCP | P1 |

**不建议系统化的部分**：

- **代码编辑器里的结对过程**。逐轮对话、补全、重试都不进系统——它们是过程，不是证据。
- **测试套件的执行结果**。绿与红留在 CI 里；系统只记 `实现状态` 达到哪一档，以及审查发现了什么。
- **代码本体**。系统不托管仓库，`13 接口契约` 里存的是**签名与契约的文本副本**，实现代码在仓库里。这是刻意的：契约稳定、实现易变，把稳定的那一半放进台账才划得来。
- **风格的具体规则**。命名该用 snake_case 还是 camelCase 属于仓库惯例，系统只在第三遍审查里记一条「结论」与「发现」。

## 3. 数据模型设计

### 3.1 表结构

空间：`科研方法`。表：`13 接口契约`（一行 = 一个待实现函数）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 契约编号 | 自动编号（前缀 `if-`） | —— |
| 函数名 | 文本（标题字段） | 如 `split_by_time` |
| 模块/文件 | 文本 | 如 `src/data.py` |
| 输入 | 多行文本 | 参数名 / 类型 / 取值范围 / 单位 |
| 输出 | 多行文本 | 返回结构 / 类型 / 边界情形形态 |
| 前置条件 | 多行文本 | 如「df 非空」「time_col 是 datetime 列」 |
| 后置条件与异常 | 多行文本 | 保证什么成立；失败时抛什么（如 `ValueError`） |
| 自检·同事能写实现 | 复选框 | 三问之一 |
| 自检·同事能写测试 | 复选框 | 三问之二 |
| 自检·无模糊措辞 | 复选框 | 三问之三：无「合理处理」「适当返回」 |
| 实现状态 | 单选 | 未实现 / AI 已生成待验证 / 已通过三档验证 / 已过三遍审查 / 已合并 |
| AI 生成行数 | 数字 | 用于步长统计 |
| 调试行数 | 数字 | 用于步长统计 |
| 关联假设 | 关联 → `假设登记`（多值） | 核心改动服务于哪条假设——代码也挂上证据链 |
| 审定三件套 | 单选 + 成员 + 时间 | 审定状态 / 审定人 / 审定时间（见 `README` 第 4.3 节） |

表：`13 AI 代码审查`（一行 = 一遍审查）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 契约 | 关联 → `13 接口契约`（单值） | —— |
| 遍次 | 单选 | 第一遍·能跑 / 第二遍·逻辑正确 / 第三遍·风格一致 |
| 结论 | 单选 | 通过 / 需修改 |
| 发现 | 多行文本 | 「建议把第二遍的发现随手记下来——一个月后你会感谢自己留下的这些『为什么』」 |
| 重点检查项 | 多选 | 下标偏移 / 空集合 / 时区与单位 / 隐式类型转换 / 异常被吞（针对第二遍） |
| 执行者 | 单选 | 机器 / 人 / 合作者 |
| 日期 | 日期 | —— |

表：`13 上下文包`（一行 = 一份给 AI 的上下文）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 任务名 | 文本（标题字段） | 如「实现 split_by_time」 |
| 仓库结构摘要 | 多行文本 | 目录树 + 一句话职责，标明「编辑这里 / 不要改」 |
| 相关接口签名 | 多行文本 | 本次改动会直接调用的签名与契约 |
| 测试样例 | 多行文本 | 1–2 个输入输出对（含行数这类具体数字） |
| 已存为项目文件 | 复选框 | 上下文模板存成项目文件，每次填空隙 |
| 文件路径 | 文本 | 如 `docs/ai_context/impl_split_by_time.md` |
| 最近更新时间 | 日期 | **保鲜期管理**：仓库结构变了、契约变了、需求变了就要更新 |

表：`13 步长记录`（轻量，可选；一行 = 一段时间的统计）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 日期 | 日期 | —— |
| 本次生成行数 | 数字 | —— |
| 本次调试行数 | 数字 | 与生成行数的比值说明步长是否合适 |
| 是否需读一会儿才能理解 | 单选 | 扫一眼即可 / 需要读一会儿——失控信号一 |
| 验证失败次数 | 数字 | 超过一次即失控信号二 |
| 是否出现「先合并了再说」 | 复选框 | 失控信号三 |
| 下次是否减半 | 复选框 | 出现任一信号时的处置 |

**关系与公式**：

- `13 接口契约` → `13 AI 代码审查`：一份契约可有多遍审查记录；「已过三遍审查」的状态由人对照审查记录数确认（不用公式，理由见第 9 节）。
- `13 接口契约.关联假设` → `假设登记`：把「代码服务于哪条假设」钉住，这是第 24 讲品味曲线的原料之一。
- **不使用跨表聚合**：`生成行数 / 调试行数` 的比值按原文是思考题（「它说明你的步长是否合适」），需要人看数字做判断，不做自动汇总。

## 5. 自动化设计

| 名称 | 触发器 | 条件 | 动作 | 防的坑 |
| --- | --- | --- | --- | --- |
| 契约在先 | `record_created` on `13 接口契约` | `实现状态 = AI 已生成待验证` 且 `自检·同事能写实现` 未勾选 | `add_comment`（“先写完契约再让 AI 动手；契约写在签名与文档字符串里，不在聊天记录里”） | 拿着模糊需求让 AI 猜设计 |
| 合并即标注 | `field_equals`（`实现状态` = 已合并） | —— | `add_comment`（“提交信息中请标注哪些代码由 AI 生成；这同时是第 20 讲 AI 使用日志的原料”）+ `create_record`（在 `AI 使用日志` 建一条，`环节 = 代码生成`，`性质 = 待判定`） | AI 生成的代码悄悄进仓库，第 20 讲披露时无据可查 |
| 步长超限即提醒 | `field_equals`（`AI 生成行数` > 50） | —— | `add_comment`（“单次生成超过 50 行：先在 `13 AI 代码审查` 记一遍逻辑审查，再把下一个任务切小一半”） | 300 行一次的生成把调试成本变成本金 |
| 第二轮审查缺失即提醒 | `field_equals`（`实现状态` = 已过三遍审查） | 关联 `13 AI 代码审查` 中无「第二遍·逻辑正确」记录 | `add_comment`（“三遍里最容易被跳过的是第二遍——能跑只说明语法没错，AI 代码最常见的恰恰是跑得通但想错了”） | 用第一遍和第三遍假装三遍做完了 |

## 6. 智能体设计

### 站内智能体

**`契约审查员`（模式：`prompt`）**

- 输入（用户提供）：一份接口契约（四要素文本），可选附上仓库里相邻函数的签名作为风格参照。
- 输出：三问的逐条回答 + 修订建议。三问即原文的三个自检：同事能否仅凭契约写出实现？能否仅凭契约写出测试？契约里有没有无法验收的措辞？
- 系统提示词骨架：

```text
你是接口契约的审查员。输入是一份契约，含输入 / 输出 / 前置条件 / 后置条件与异常四部分。

【任务】按顺序回答三个问题，每个问题都要给出「能/不能」的结论与具体理由：
1. 一个不了解本项目的同事，能否仅凭这份契约写出实现？指出他一定会问你的地方；
2. 他能否仅凭这份契约写出测试？指出无法构造的测试用例；
3. 契约里有没有无法验收的措辞（如「合理处理」「适当返回」「尽量快」）？逐处引用原文。

【硬约束】
- 你只审契约，不写实现，也不改字段；
- 发现的问题按「必须修 / 建议修」两档列出；
- 不允许把「契约写得很长」当作完备——完备的标准是能被独立验收。
```

### 外部 MCP 工作流

1. **契约 ↔ docstring 一致性校验（P1）**：外部 Agent 用 MCP 读 `13 接口契约` 的签名与四要素，再用 Grep 读仓库里对应函数的文档字符串，输出差异清单（契约改了、docstring 没改，或反之）。
2. **生成行数回填（P1）**：从 git diff 统计与契约相关的改动行数，回填 `AI 生成行数` / `调试行数`，供 `步长失控排查` 视图使用——比人凭印象填准。
3. **缺陷模式回流**：从第 16 讲 `16 调试记录.错误模式` 拉「AI 意图误解」「AI 接缝不一致」两类记录，按契约分组，指出哪些契约的哪一段反复出问题，供修订参考。

### 红线（AI 只能给草稿）

- **契约由人写**。可以让 AI 审契约，但不允许让 AI 起草契约——起草契约就是让出设计权，这正是本讲第一章要拦住的事。
- **`实现状态` 由人推进**。AI 不能把状态自己改成「已通过三档验证」；三档验证的每一档都是可核验的动作，必须有人跑过。
- **第三遍审查由人或合作者做**。风格一致性的判断基于仓库惯例的隐性知识，AI 每次看到的上下文都不完整。
- **`13 AI 代码审查.发现` 人手写**。审查发现是最值得留存的「为什么」，不能由 AI 生成。

## 7. 与其他讲的接口

- **上游**：`假设登记`（`关联假设`——核心改动服务于哪条假设）。
- **下游**：
  - 第 16 讲：AI 代码的缺陷模式与接缝问题进 `16 调试记录.错误模式`，反过来改契约写法——这是本讲与第 16 讲的双向喂养。
  - 第 20 讲：代码生成是实质性使用，合并时自动建 `AI 使用日志` 条目，成为披露原料。
  - 第 12 讲：代码提交哈希进 `12 环境指纹`（`git 提交哈希` 字段）。
  - 第 22 讲：核查清单的合规区会看「AI 生成代码是否已登记并披露」。
- **单一事实来源**：**契约只在本表**；代码仓库里的签名与 docstring 是可执行副本，两者不一致时以本表为准并同步修正一处。**代码本身不进系统**——系统不托管仓库。

## 8. 分期实施与验收

### P0（纯配置，零代码）

1. 建 `13 接口契约`（自动编号 `if-`）、`13 AI 代码审查`、`13 上下文包`、`13 步长记录`。
2. 建视图：契约未齐 / 待审查 / 步长失控排查 / 审查记录 / 上下文过期。
3. 建两个表单视图：`写一份契约`、`记一遍审查`。
4. 建四条自动化：契约在先 / 合并即标注 / 步长超限即提醒 / 第二轮审查缺失即提醒。
5. 建站内智能体 `契约审查员`，提示词入 `提示词库`。
6. 打通与第 20 讲的接口：`AI 使用日志` 的建条目动作（该表在第 20 讲定义，P0 阶段先手动登记）。
7. 上下文模板存成项目文件（`docs/ai_context/`），`13 上下文包.文件路径` 指向它。

### P1（少量增强）

| 需求 | 说明 | 建议落点 |
| --- | --- | --- |
| 契约 ↔ docstring 一致性校验 | 现在靠人对照 | MCP 工作流 + 脚本 |

### P2（可选）

- 契约库导出为项目内的接口文档（Markdown），给新加入的合作者读。
- 按 `关联假设` 统计「一条假设动过多少份契约、生成多少行代码」——它是研究工作的工程量侧写。

### 验收标准

1. `契约未齐` 视图长期为空：允许 AI 生成实现之前，三个自检全部勾选。
2. `13 AI 代码审查` 中**第二遍**的 `重点检查项` 至少填过一项，且 `发现` 非空——第二遍必须留下实质性内容。
3. `步长失控排查` 里的每一条都能指向一条处置：下一批请求已切小一半（`13 步长记录.下次是否减半` 勾选）。
4. 每个 `实现状态 = 已合并` 的契约，在 `AI 使用日志` 里有一条对应的代码生成条目。
5. `13 上下文包` 里的每一份都 `已存为项目文件`，且 `最近更新时间` 在最近一次目录结构调整之后。

## 9. 与原文的偏差说明

| 偏差 | 原文做法 | 本设计做法 | 理由 |
| --- | --- | --- | --- |
| 「50 行」的上限 | 经验上限，靠自律 | 做成可统计字段（`AI 生成行数` / `调试行数`）并建 `步长失控排查` 视图 | 原文的思考题第 2 问要「统计生成行数与调试行数的比值」——不落成字段就没法统计，只能靠回忆 |
| 三个失控信号 | 自查的三条感觉 | `13 步长记录` 的三个列（需读一会儿 / 失败次数 / 先合并了再说） | 把感觉变成数据：出现任一信号时留下一条记录，才能看出「哪类任务总是失控」 |
| 三遍审查 | 一次性的三个动作 | `13 AI 代码审查` 独立成表，一行一遍，含 `重点检查项` 多选 | 原文的思考题第 3 问是「哪一遍最容易被你跳过」——只有把三遍拆成三行，这个问题才回答得了 |
| 「能跑就合并」 | 常见误区里点名 | `跳过第二遍` 视图专门捞「标成已过三遍审查但第二遍没记录」的契约 | 最常见的偏差不是不做三遍，而是**把第一遍和第三遍做完就宣布三遍做完了** |
| 契约的位置 | 「写在函数签名与文档字符串里」 | 系统里也存一份契约文本，并计划做一致性校验 | 只放在仓库里，契约就无法参与「哪条假设 → 哪些契约 → 多少行代码」的关联；代价是两份副本，故 P1 加校验 |
| 上下文模板 | 「存成项目文件，每次填空隙」 | 表里加 `最近更新时间` + `上下文过期` 视图 | 原文提醒了「保鲜期」，但没有可检查的抓手；一个日期字段就能把提醒变成清单 |
