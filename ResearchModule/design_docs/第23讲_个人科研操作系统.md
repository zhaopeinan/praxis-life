# 第 23 讲 个人科研操作系统：系统落地设计

> 来源：`../design_principle/第23讲_个人科研操作系统把模板沉淀为系统.pdf`
> 落地度：★★★★★（高）｜ 依赖：第 01–22 讲全部 ｜ 主体分期：P0（月/学期复盘的自动提醒需 P1）
> 主产物：共享表 `模板库`（定义于此讲，全书共用）+ 表 `23 复盘记录`（三级复盘各一行）+ 表 `23 年度回顾`（一年一行）

## 1. 本讲方法要点

1. **单点工具的价值是线性的，系统的价值是复利的**。前二十二讲攒下的十几件工具「各自都很好用，却散落在不同的笔记、表格和记忆里——换一台电脑丢一半，换一个项目忘一半」。
2. **操作系统的核心不是工具的数量，而是组件之间的接口**。接口体现在引用关系上：预期结果卡的「假设编号」指回假设登记表、配置文件的编号指回预期结果卡、实验记录的备注指向配置文件、写作流水线的每个数字指回实验记录、核查清单的每条检查项指回相应记录。**一条从「决策」到「投稿」的完整证据链就此闭合——论文里的任何一句话，都能沿接口回溯到一条原始记录**。
3. **系统落地的第一条纪律是单一事实来源**：每类信息只在一个地方维护。假设状态只在登记表里更新，不散落在聊天记录与幻灯片里；模板只在一个库里存放，不在五个笔记软件里各存一份互相矛盾的版本。**形态不重要——唯一性与可检索性才重要**。
4. **新组件入库要过闸**——三问：**它防的坑我实际踩过吗？它与现有哪个组件接口？我承诺在什么例程里维护它**？三问答不出，说明它是「看起来很专业」的杂物——放进冷藏清单，踩过坑再转正。
5. **模板不是一次设计终身使用的产品，而是被真实失败持续修正的文档**。迭代纪律只有一条：**每被坑一次，改一版模板**。你的模板库因此携带着你的全部历史教训——它比任何通用清单都更适合你。
6. **模板库的三样东西**：**版本号**（每次修改递增）、**变更日志**（每条修改注明触发事件，「因为某次某坑而增加此条」）、**存放位置**（一个你天天会打开的地方）。**变更日志的价值在复盘时显现**：一年后重读，你能清晰看到自己的薄弱环节从「文献」迁移到「统计」的轨迹。
7. **反向纪律：模板做减法**。连续三个月没有触发过任何一次使用的字段，删掉；让填写变得痛苦的结构，简化。**系统的成功标准不是完备，而是被坚持使用**——维护成本高于取用价值的系统注定被放弃。
8. **模板库设一个数量上限：核心模板不超过十件**。超过这个数，通常说明你在收集模板而非使用系统。
9. **团队与学生场景的两层价值**：模板库是新人培训的核心资产（与其手把手教三个月，不如让新人按模板跑一个小项目）；它把「导师的品味」从不可言传的直觉变成可讨论的文本——**争议从「你为什么让我这么改」变成「模板哪一条适用于这里」**。
10. **三级复盘例程按时间尺度分工**：
    - **周复盘**（30 分钟，周五下午）：**只管执行层**。三项固定议程——数据完整性（核对本周实验记录的六字段完整率）、假设状态（更新假设登记表）、下周排程（选出一条假设进入「验证中」）。**逐项过表，不即兴发挥**。
    - **月复盘**（半天）：**看方向层**。当前项目的进展是否还在预期路径上；选题决策日志里本月到期的「预期验证点」逐个回验；模板库本月有无触发修改的坑。**产物是一页纸：进展、偏差、下月调整**。
    - **学期复盘**（一天）：**看战略层**。产出盘点与研究纲领的契合度；能力短板识别（品味、工具链还是声誉那条线欠账）；下学期一到三个重点方向，以及明确的**「不做什么」清单**——**学期复盘最重要的产物往往是后者**。
11. **三级复盘共同的铁律是写下结论**：**没有落盘的复盘约等于没有发生**。时间比例大致是：周复盘占维护时间的十分之七，月复盘十分之二，学期复盘十分之一。**频率与深度成反比不是巧合——越高频的例程，越要短到不可能失败**。
12. **例程坚持不下来，通常死于两种病**：其一是**时间槽被挤占**（复盘没有固定日历位置，就会在任何一件「更急」的事面前让位——治疗办法是把三级复盘写进日历并设为不可协商）；其二是**复盘退化为感想**（不看数据、只谈心情的复盘三周内就会变成自我表扬仪式——治疗办法是**议程第一条永远是「打开表格」，让记录说话，而不是让记忆说话**）。
13. **AI 年度回顾四步**：① **汇总导出**（各组件导出为结构化文本，脱敏处理未公开数据与涉密信息）；② **附上数据字典**（说明每个字段的含义、单位与取值范围——**字段含义模糊的表格，AI 也只能返回模糊**）；③ **分轮提问，由粗到细**（第 1 轮全景：产出结构、时间分配、项目存活率；第 2 轮模式：哪类决策判断失误、失误的共同特征；第 3 轮反直觉：三个「我以为做得好、数据却不支持」的地方；第 4 轮建议：三条工作流修改，每条注明依据的数据）；④ **人下结论**（AI 出的所有「模式」都是待检验假设，不是结论——**它说你在 X 类决策上频繁失误，就翻出那几条决策日志重读**）。
14. **年度判断报告固定为三栏结构**，避免写成散文感想：**【数据】**支持本结论的原始记录编号与关键数字；**【模式】**数据中浮现的判断或习惯模式（**注明 AI 提出、人已验证**）；**【行动】**对应的工作流修改条款，写明验收方式与检查时点。
15. **一条数据边界**：AI 只能看到被记录的部分。指导学生的投入、建立合作的时间、阅读与思考的「暗时间」不在表里，**年度回顾的结论要为此留出余量**。
16. **年度回顾的产出必须回灌系统**：三条修改条款以变更日志的形式写入模板库，「不做什么」清单进入下学期复盘的基线。**不回灌的回顾是消费，回灌的回顾才是投资**。

| 年度回顾员智能体 | 站内智能体（模式 `tools`） | 智能体 | P0 |
| 系统健康度仪表盘 | count / line / bar | 仪表盘 | P0 |
| 复盘习惯的坚持统计 | **不做打卡**——原文明确反对把坚持变成表格 | —— | —— |

**不建议系统化的部分**：

- **「系统集邮」是这个设计明确反对的对象**：不建五层目录；全系统只有一层表名前缀。**不做「目录树」字段，不做「组件关系图」的自动生成**——组件关系由各讲的关联字段承担，再画一张图只会多一份会过期的副本。
- **复盘不打卡**。三级复盘不做 streak、不做完成率。原文的要点是「越高频的例程，越要短到不可能失败」——**打卡制的失败模式恰好相反：它把失败本身变成了可记录的负担，从而加速例程的死亡**。`23 复盘记录` 只记录已经发生的复盘，不记录「本该发生但没发生的复盘」。
- **暗时间不进系统**。指导学生的投入、建立合作的时间、阅读与思考的时间——AI 只能看到被记录的部分，年度回顾的结论要为此留出余量。给这类时间建一张表，等于用记录的假象替换了真实。
- **「模板哪一条适用于这里」的讨论**不进系统。它是导师与学生之间的对话；系统只把模板变成可引用的文本，不承担对话本身。
- **年度判断报告的散文部分**不进字段。三栏结构是骨架，结论的表述仍是人写的；文档承载它，表只承载可检索的元数据（年份、依据、三条条款）。

**关系与公式**：

- `24 研究纲领.修订依据` → `23 年度回顾`（第 24 讲定义）：**年度回顾是纲领修订的输入**。
- `三条修改条款` 与 `模板库.变更日志` 之间**不建关联字段**——条款是「要改什么」的声明，变更日志是「已经改成什么」的证据；两者由人对照，硬关联会让「条款写了但没执行」这件事被系统的关联自动掩盖。
- **不使用跨表聚合**：`模板库` 与各讲表之间没有数量关系。「某一讲建了表但一直没数据」用仪表盘的 bar 图看（各讲表的数据量分布），不在表内计算。

### 3.2 记录样例

**样例 1（`模板库` 的一行——带完整变更日志的模板）**

| 字段 | 值 |
| --- | --- |
| 模板名 / 类型 | 核查清单·统计区 / 清单 |
| 来源讲次 | 22、23 |
| 版本 | 3 |
| 变更日志 | v2：增加「种子数量 n 明确写出」——因为审稿人问住了种子报告；<br>v3：增加「除 p 值外报告效应量或置信区间」——因为在月复盘里发现三篇论文的显著性表述都被同一类质疑 |
| 触发事件 | 审稿人第 2 轮意见 rv-09；月复盘 2026-05 的「重复出现的意见类型」 |
| 最近更新 / 单一事实来源 | 2026-05-20 ／ ✅ |
| 存放位置 | 科研方法空间 → `核查模板` 表（统计区五行） |

记录写法：**每一条变更都指回一个具体的事件**（一条审稿意见、一次月复盘）——这正是「模板库携带你的全部历史教训」的具体含义。

**样例 2（`23 复盘记录` 的三行——三级各一行）**

| 级别 | 议程 | 发现 | 调整 | 不做清单 | 耗时（分钟） |
| --- | --- | --- | --- | --- | --- |
| 周复盘 | 数据完整性 / 假设状态 / 下周排程 | 本周 4 条运行记录里 2 条的「备注」为空 | 补齐备注；下周把「验证中」名额给 H07 | —— | 28 |
| 月复盘 | 进展路径 / 预期验证点回验 / 模板改动 | 三条到期的预期验证点回验了两条，一条判断失误（低估了数据清洗成本）；核查模板改了一处 | 下月把数据准备时间按 2 倍估 | —— | 190 |
| 学期复盘 | 产出盘点 / 纲领契合度 / 能力短板 / 下学期重点 | 产出两个（一篇主干、一个开源工件）；工具链那条线欠账最多 | 下学期重点：把评测流程模板化 | **不接跨方向的短期合作**；**不再为凑完整性给每张表都加字段** | 410 |

记录写法：**学期级的 `不做清单` 才是它最有价值的产物**——「不接跨方向的短期合作」这条判断的含金量，高于任何一条「下学期要做什么」。

**样例 3（`23 年度回顾` 的一行——三栏结构与数据边界）**

| 字段 | 内容 |
| --- | --- |
| 年份 / 导出范围 | 2026 ／ 决策日志、假设登记、实验记录、投稿与审稿记录、月复盘 |
| 脱敏完成 / 数据字典 | ✅ ／ 12 张表、各字段含义与单位（含「工作量 = 1-5，1 为半天以内」等） |
| 第 1 轮·全景 | 产出结构：一篇主干论文 + 一个开源工件；时间分配：实验 45%、写作 25%、文献 20%、其他 10%；项目存活率：3 个方向中 1 个被证伪关闭 |
| 第 2 轮·模式 | 三类决策事后被证明失误的共同特征：**都在数据准备阶段低估了两倍以上成本** |
| 第 3 轮·反直觉 | ① 我以为文献阅读投入充足，但 `文献库` 的新增记录在下半年下降了 60%；② 我以为审稿回应很迅速，但 `实际一审周期` 之后的平均回应天数是 21 天；③ 我以为模板库在频繁更新，实际 `最近更新` 显示三分之二的模板一年内没动过 |
| 三条修改条款 | ① 数据准备的时间估算一律乘 2（依据：`04 选题决策日志` 的 D-07/D-11/D-15）；② 审稿意见到达后 72 小时内完成分类（依据：`21 审稿意见` 的回应天数）；③ 每季度至少更新一个模板（依据：`模板库.最近更新`） |
| 边界备注 | 本年度指导学生投入约 200 小时、跨机构合作 3 次——**均不在上述数据中**，结论需为此留出余量 |

记录写法：第 3 轮的三个反直觉点是**这份回顾真正的产出**——前两轮 AI 能替你摆平，第三轮必须自己诚实。

## 4. 视图与交互设计

**主视图与筛选口径**：

- `模板库` 的三个闸门视图各管一条纪律：`无变更日志`（模板没在吸收教训）、`单一来源违规`（同一模板存在两处副本）、以及 P1 的「三个月未用」（待减法的字段）。**三者的共同点是「安静地腐坏」**——不建视图就永远看不见。
- `23 复盘记录` 的 `未落盘` 是本讲最重要的一条闸门：**没有写下来并归档的复盘，等于没有复盘**。它是唯一能验证「复盘真的发生了」的字段。
- `历史对照`（按年份升序）是年度回顾的「跨年视图」：看「我以为」与现实的差值是在缩小还是扩大——**这个差值的变化趋势，就是品味曲线的斜率**。

**日历与仪表盘怎么配**：

- **三级复盘写进日历并设为不可协商**（原文的治疗办法）。系统侧：`23 复盘记录` 用 calendar 视图绑定 `日期`，每周五的外观即是这一年的复盘密度；ICS 日历订阅可以把复盘时段推到系统日历里，做到「不可协商」。
- `系统健康度` 仪表盘：count（模板数 / 复盘次数 / 单一来源违规数）、line（`模板库` 版本的年度增长）、bar（各讲表的数据量分布）。**最后一张图是本讲最有用的诊断**——它发现「某一讲建了表但一直没数据」，**这是系统里最先烂掉的组件**。

**记录详情页布局**：

- `模板库`（分组样式，两列）：分组 1「身份」：模板名 / 来源讲次 / 类型 / 版本 / 状态；分组 2「内容」：正文 / 存放位置；分组 3「迭代」：变更日志 / 触发事件 / 最近更新 / 单一事实来源。
- `23 复盘记录`（分组样式，两列）：分组 1「场次」：级别 / 日期 / 议程 / 耗时；分组 2「内容」：发现 / 调整 / 不做清单；分组 3「落盘」：结论落盘 / 归档位置。
- `23 年度回顾`（分组样式，两列）：分组 1「准备」：年份 / 导出范围 / 脱敏完成 / 数据字典；分组 2「四轮提问」：第 1 轮·全景 / 第 2 轮·模式 / 第 3 轮·反直觉；分组 3「结论」：年度判断报告 / 三条修改条款 / 完成日期。

**表单**：

- `记一次复盘`：字段限定为 级别 / 日期 / 议程 / 发现 / 调整 —— **议程是必填的第一个字段**，它的作用是让「打开表格」成为动作的第一步。
- `登记一个模板`：字段限定为 模板名 / 类型 / 来源讲次 / 存放位置 / 单一事实来源 —— **入库三问的答案要能填满这个表单**（防的坑 → `触发事件`；与谁接口 → `来源讲次`；在哪维护 → `存放位置`）。

**文档**：

- 年度判断报告用系统内文档承载，三栏结构（数据 / 模式 / 行动）写在模板头部。
- 三级复盘的归档各归其位：周复盘 → 项目日志（文档），月复盘 → 月度文档，学期复盘 → 年度档案。**`归档位置` 字段记录它们的去向**。

## 5. 自动化设计

| 名称 | 触发器 | 条件 | 动作 | 防的坑 |
| --- | --- | --- | --- | --- |
| 周五周复盘 | `schedule weekly:5:17:00`（绑定 `23 复盘记录`） | —— | `feishu_bot`（本周复盘三件事：数据完整性、假设状态、下周排程）+ `create_record`（建在绑定的这张表里建一条周复盘空记录——同表，合规用法） | 复盘没有固定日历位置，就会被任何一件「更急」的事推掉 |
| 月度复盘提醒（**P1 受限**） | 现有能力下用 `schedule weekly:1:09:00`（每月第一周的周一）兜底 | —— | `feishu_bot`（“月复盘看方向层：进展路径、预期验证点回验、模板改动；议程第一条是打开表格”） | cron 只到周级——**P1 建议新增 `monthly:DD:HH:MM` 与 `quarterly` 语法，落点 `src/store.ts` 的 cron 解析处** |
| 模板更新回写 | `field_equals`（`模板库.状态` = 实验中） | —— | `add_comment`（“模板改了哪一条，把它钉在 `23 复盘记录` 的调整栏里，让变更可追”） | 模板改了却没人知道为什么改 |

**关于「月度复盘提醒」的降级**：这是本设计中**唯一一条被能力边界显著影响的主线功能**（`create_record` 只能建在绑定表里，本条恰好同表，不受此限）。周级 cron 无法精确到「每月一号」或「每学期初」，因此 P0 的月/学期复盘靠两件事兜底：① 每周提醒里的文字说明（「本周是本月第一周 → 今天做月复盘」）；② ICS 日历订阅 + 人工日历上的固定时段。**P1 的价值很高**，因为月复盘是「模板迭代」的主要触发点。

> 自动化的四条动作边界（动作作用范围限于触发记录或同库指定表、动作之间无分支、`notify` 须指定接收人、`field_equals` 会重复命中）见 `README.md` §3 与 `_系统能力现状.md` §2。

## 6. 智能体设计

### 站内智能体

**`年度回顾员`（模式：`tools`）**

- 工具：`query_records`（按 `导出范围` 读取各表）+ `create_record`（把四轮提问的原始回答写入 `23 年度回顾` 的对应字段）。
- 系统提示词骨架（照搬原文 Listing 23.1 的分轮提问，并加数据边界声明）：

```text
你是年度回顾的提问者与整理者。我会给你一年的科研记录（已脱敏）与数据字典。
请分四轮提问，每轮基于我的回答继续，不要跳轮：

第 1 轮（全景）：这是这一年的科研记录{数据+字段说明}。请给出产出结构、时间分配、项目
  存活率的整体描述。
第 2 轮（模式）：从决策日志与假设登记表分析：我在哪类决策上事后被证明判断失误？失误的
  共同特征？
第 3 轮（反直觉）：指出三个「我以为做得好、数据却不支持」的地方。
第 4 轮（建议）：基于以上，给出明年工作流的三条具体修改，每条注明依据的数据。

【硬约束】
- 你说出的每一个模式都必须在数据里有对应的记录编号；找不到对应记录的模式不要提；
- 你只能看到被记录的部分：指导学生、建立合作、阅读与思考的「暗时间」不在数据里，涉及
  这些方面时明确声明「数据不覆盖」；
- 你给出的所有「模式」都是待检验假设，输出时必须这样标注——最终结论由我下，你在结论
  字段里只记录我的原话。
```

**`模板减法员`（模式：`prompt`）——可选，季度启用**

- 输入：`模板库` 全表（含 `最近更新`、`版本`、`触发事件`）。
- 输出：建议做减法的清单——连续三个月未更新的模板、正文超过一屏的模板、`变更日志` 为空且版本为 1 的模板。
- 定位：**它的输出是建议，删不删由人定**——原文的减法纪律是「连续三个月没有触发过任何一次使用的字段，删掉」，而「有没有被使用」这件事只有你知道。

### 外部 MCP 工作流

1. **年度导出与脱敏（P0）**：用空间级 Zip 导出（tables JSON/CSV + documents Markdown）生成 `导出范围` 里的各表数据，脱敏后交给 `年度回顾员`——**导出与脱敏这一步必须人工确认 `脱敏完成` 后才进行**。
2. **系统健康巡检（P1）**：外部 Agent 统计各表的数据量与最近写入时间，输出「建了表但 90 天无数据」的清单——它是仪表盘那张 bar 图的定时版本，也是「系统里最先烂掉的组件」的定期体检。
3. **接口双向可达检查（P1）**：对照各讲文档的「接口」小节，验证每条关联字段都双向可达（`A → B` 与 `B → A` 都存在）——**回答「操作清单」第 1 条「检查每个接口是否双向可达」**。

### 红线（AI 只能给草稿）

- **年度回顾的结论由人下**：AI 摆平数据，你对自己诚实。**AI 出的所有「模式」都是待检验假设**，逐条对照原始记录验证后才能进 `年度判断报告`。
- **第 3 轮反直觉提问不可跳过，也不可由 AI 代答**：它要求的是「我以为 vs 数据」的对照，只有你能提供「我以为」那一侧。
- **`三条修改条款` 必须人写**：AI 可以建议，但条款的措辞与验收方式是人对自己下的承诺。
- **暗时间的边界必须显式声明**：任何涉及「指导学生、建立合作、阅读思考」的结论，AI 必须声明「数据不覆盖」——**这是防止回顾变成「数据决定论」的唯一手段**。
- **模板的删除由人决定**：`模板减法员` 只给清单。

## 7. 与其他讲的接口

- **上游**：全部前 22 讲的表。具体地：`04 选题决策日志`（月复盘的「预期验证点回验」）、`15 实验记录`（周复盘的「数据完整性」）、`21 审稿意见`（月复盘的「重复出现的意见类型」）、`22 核查清单`（年度回顾的质量数据）、`模板库` 自身（全书的模板受版本管理）。
- **下游**：
  - `24 研究纲领`：年度回顾 → 纲领修订（`修订依据` 关联）。
  - 全部讲次：模板迭代（`模板库` 的变更 → 各讲的表结构/视图/自动化/提示词随之更新）。
- **单一事实来源**：**每类信息只在一个地方**——这句话在系统里的实现就是 `模板库.单一事实来源` 字段 + 各讲文档的「单一事实来源」小节。**本讲是全书的元讲次：它维护的不是某一类数据，而是「数据之间的关系」**。

## 8. 分期实施与验收

### P0（纯配置，零代码）

1. 建三张表：`模板库`（共享）、`23 复盘记录`、`23 年度回顾`。
2. **回填 `模板库`**：把前 22 讲文档里的提示词、检查清单、文档模板、视图配置逐条登记（预计 20–30 条，**其中核心模板控制在 10 件以内**）。
3. 建视图：模板侧的 按类型分组 / 变更轨迹 / 无变更日志 / 单一来源违规；复盘侧的 周复盘 / 月复盘·待回验 / 学期重点与不做清单 / 未落盘；年度侧的 当年 / 历史对照。
4. 建两个表单视图：`记一次复盘`、`登记一个模板`。
5. 建自动化：周五周复盘（`weekly:5:17:00` 绑定 `23 复盘记录` + `feishu_bot` + `create_record`，同表）；月度提醒用 `weekly:1:09:00` 降级实现；模板更新回写。
6. 建站内智能体 `年度回顾员`（年底启用）与 `模板减法员`（季度启用）；提示词入 `提示词库`。
7. 建仪表盘 `系统健康度`（含各讲表的数据量分布 bar 图）。
8. 建年度判断报告文档模板（三栏结构）。
9. 打通接口：`24 研究纲领.修订依据` → `23 年度回顾`（第 24 讲建字段时接上）。

### P1（少量增强）

| 需求 | 说明 | 建议落点 |
| --- | --- | --- |
| cron 增加 `monthly` / `quarterly` 语法 | 月复盘与学期复盘的精确提醒；**本讲最主要的 P1** | `src/store.ts` 的 cron 解析处 |
| 「三个月未用」的相对日期过滤 | 自动化条件已可用 `最近更新 < today-90`（2026-10-18 落地）；做成**视图过滤**仍未支持 | 视图条件支持相对日期比较 |
| 年度导出 → 脱敏 → 分轮提问的半自动化 | 现在是手工导出 + 人工脱敏 | MCP 工作流 |
| 接口双向可达检查 | 现在靠人对照各讲的「接口」小节 | MCP 工作流 |
| 系统健康巡检（90 天无数据的表） | 现在是仪表盘的一张图 | MCP 工作流 + `schedule` |

### P2（可选）

- 复盘耗时的分布统计（对照「30 分钟 / 半天 / 一天」的设计）——**它发现的是「复盘正在退化为感想」的早期信号：耗时腰斩**。
- 模板库的年度增长曲线接入年度判断报告的第 1 轮全景。
- 各讲表的数据量分布做成趋势线而非快照，看哪一讲的表在「长出来」、哪一讲在「烂掉」。

### 验收标准

1. `单一来源违规` 视图为空：每个模板都只有一个维护位置。
2. `无变更日志` 视图为空（或其中只有本季度新建的模板）：**模板库在吸收教训**。
3. 每月至少一条月复盘记录，且 `议程` 含「预期验证点回验」；每学期至少一条学期复盘记录，且 `不做清单` 非空。
4. `未落盘` 视图为空：每次复盘都有结论并归档。
5. 年度回顾的 `三条修改条款` 已回灌——**在下一年度的 `模板库.变更日志` 里能找到每一条条款对应的变更**。
6. 抽查一条年度回顾的「模式」：能在原始记录里找到对应的记录编号（`年度判断报告` 的【数据】栏可复现）。
7. 抽查仪表盘的各讲表数据量分布：**不存在「建了表但 90 天无数据」的表**（或已确认该表在当前阶段不需要数据）。

## 9. 与原文的偏差说明

| 偏差 | 原文做法 | 本设计做法 | 理由 |
| --- | --- | --- | --- |
| 组件图（表 23.1） | 8 个组件（模板） | 12 张共享表 + 每讲私有表 | 原文的 8 个组件是「模板」，而系统里**模板与数据必须分离**：`模板库` 存模板，各讲表存数据——这个分离正是「模板可迭代而不污染历史」的前提，也是第 22 讲「定义表 + 记录表」的同一逻辑 |
| 模板库的形态 | 「一个 git 仓库就能同时承担版本号与变更日志」 | 系统内表（`模板库`），`版本` 数字 + `变更日志` 多行 | 原文的 git 方案依赖命令行习惯；系统内表的优势是它可以被 `模板减法员` 读、被年度回顾导出、被各讲文档引用。**代价是失去了 diff——故 `变更日志` 必须写得足够具体才能补偿** |
| 三级复盘的时间槽 | 「写进日历并设为不可协商」 | `23 复盘记录` 的 calendar 视图 + ICS 日历订阅 + `weekly:5:17:00` 提醒 | 系统无法强制「不可协商」，但可以把时间槽变得可见、可订阅——**剩下的执行纪律取决于你，这一点不改** |
| 复盘不打卡 | 未明确，但通篇强调「被坚持使用」 | **明确不做打卡、不做 streak** | 打卡制的失败模式与本讲的治疗方向相反：它把失败本身变成可记录的负担，加速例程死亡。因此 `23 复盘记录` 只记录已经发生的复盘 |
| 新增组件三问 | 三问的提问方式 | 落成录入表单的必填字段（触发事件 / 来源讲次 / 存放位置） | 三问的价值在于**在录入时被迫回答**；做成表单必填是唯一能预置这个停顿的地方 |
| AI 年度回顾的轮次 | 四轮提问（含第 4 轮建议） | 表只有第 1–3 轮字段，第 4 轮的产物落在 `三条修改条款` | 第 4 轮的建议输出直接就是 `三条修改条款`——多设一个字段会产生两份可能不一致的副本（单一事实来源） |
| 「不回灌的回顾是消费」 | 一句话警告 | 验收标准第 5 条：下一年度的 `模板库.变更日志` 里必须能找到每条条款对应的变更 | 这是本讲唯一可以用验收标准强制执行的闭环；**把它写进验收标准，是为了让「回灌」在跨年时仍可验证** |
