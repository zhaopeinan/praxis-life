# 第 08 讲 个人知识库：让文献资产复利：系统落地设计

> 来源：`../design_principle/第08讲_个人知识库让文献资产复利.pdf`
> 落地度：★★★★★（高） ｜ 依赖：第 05–07 讲 ｜ 主体分期：P0
> 主产物：表 `08 文献关系`（四类关系链接）+ `08 主题索引`（每个活跃主题一页：条目评语 + 共识三行 + 开放问题三行）+ `08 维护日志`（每周 30 分钟例程的留痕）

## 1. 本讲方法要点

1. **知识库的价值不在收藏而在取用**。「我上次读到的那个方法在哪篇里」能在 30 秒内回答，知识库才算活；答不上来的收藏量越大越像负债。
2. **四类关系链接：上承、冲突、共享假设、部件复用**。四类比「相似」一词精确，因为各有用途：上承写引言（谁给了这条路）、冲突写张力（综述张力段落的原料）、共享假设防重复（同一个前提被两篇文章都默认了）、部件复用做实验（代码/数据/协议能借）。
3. **关联必须写「在哪个条件下」**。冲突要写清在什么条件下结论相反，部件复用要写清借哪一块——没有条件的关联等于没有关联。
4. **每个活跃主题一页索引**：条目评语（代表性文献各一句）+ 共识三行 + 开放问题三行。索引不是目录，是「这个主题我知道什么、还不知道什么」的快照，**三行是上限**（写第四行说明该拆分主题了）。
5. **双向工作流**：入库时 AI 起草、人审定；出库时**带上下文提问**——给 AI 的从来不是「我的知识库知道什么」，而是「这是主题索引与相关条目，请基于它们回答」。
6. **出库回答必须回库核对**。AI 回答里的每个论断标出对应条目，回原文核对后才采用——与第 06 讲的核查纪律同源（挂 `复核记录`）。
7. **每周 30 分钟维护例程**：清箱（处理未分类的条目）、修链（新建或修正关系）、更索引（更新共识与开放问题），**超时即停**。维护是给系统保鲜，不是把系统做大。
8. **三条误区**：只囤不拆（收藏过百、评语寥寥）、AI 批量直填（AI 生成的索引没有任何人读过）、目录完美主义（花时间整理结构树而不是回答问题）。

## 2. 可落地性判定

| 能力点 | 落地形态 | 依托的现有能力 | 优先级 |
| --- | --- | --- | --- |
| 关系网络 | 表 `08 文献关系`，一行 = 一条链接 | 双向关联 `文献库`、单选、自动编号 `L-` | P0 |
| 主题索引页 | 表 `08 主题索引` + 一页 Markdown 索引正文 | 文档挂靠、多行文本、受控词表 | P0 |
| 索引的受控词表 | `主题标签` 与 `文献库.主题` 共用一套选项 | 单选选项词表 | P0 |
| 维护例程 | 表 `08 维护日志` + 周五定时提醒 | `schedule weekly:5:17:00` + `feishu_bot` + `create_record` | P0 |
| 休眠主题发现 | `休眠待归档` 视图（90 天未更新） | 过滤、日期 | P0 |
| 跨条目问答 | 站内智能体 `跨条目提问机`（带上下文提问） | `tools` 模式 + `query_records` | P0 |
| 新条目必须连链 | 「新条目须连链」自动化 | `record_created` on `文献库` + `add_comment` | P0 |
| 出库论断回库核对 | 智能体输出强制挂 `复核记录`（第 04 讲） | 复核记录表 | P0 |
| 张力原料供给 | `冲突对` 视图 → 第 07 讲张力探针 | 过滤 | P0 |

**不建议系统化的部分**：

- **目录完美主义**。本设计**拒绝**提供二级分类目录字段——只留 `主题` 多选 + `状态` 三档。这是对原文误区三的制度性服从：结构越细，维护越贵，回答越快不了。
- **笔记软件的替代**。散点笔记（临时想法、剪藏）可以继续存在，但不能作为关系与索引的事实来源——系统只维护「关系」与「索引」这两件事。
- **全文检索与向量召回**。系统不提供「按正文内容搜文献」；取用靠关系与索引，不靠搜索。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 日期 | 日期 | 例程执行日 |
| 清箱 | 数字 | 处理了几条未读/待判决条目 |
| 修链 | 数字 | 新建或修正了几条关系 |
| 更索引 | 数字 | 更新了几个主题页 |
| 超时即停 | 复选框 | 30 分钟到时手中任务的处理：挂进「遗留」下次继续 |
| 遗留 | 多行文本 | 本次没做完的，下次从这里开始 |
| 备注 | 多行文本 | —— |

**建议视图**：见第 4 节。

**关系与公式**：

- `文献库`（第 06 讲）↔ `08 文献关系`：`关联关系` 反向关联；关系是两个文献之间的有向边。
- `08 主题索引` ↔ `文献库`：`关联文献` 多值关联；`文献库.主题` 的选项与 `主题标签` 同词表。
- **不使用跨表聚合**：「主题有几篇文献」用 `关联文献` 的关联计数（查看时可见），不做表内公式。

### 3.2 记录样例

**样例 1（一条「冲突」关系——它有明确的使用者：第 07 讲的张力探针）**

| 字段 | 值 |
| --- | --- |
| 关系编号 | L-14 |
| 源文献 | Freshness-Aware Retrieval（第 06 讲样例 1） |
| 目标文献 | Wang et al. 2025 生成端引用对齐（**需核实**） |
| 关系类型 | 冲突 |
| 说明 | 在「错答根因在哪个环节」上结论相反：源文献主张改进检索打分（检索端），目标文献主张约束生成引用（生成端）。**成立条件**：源文献的结论建立在「元数据完整」的前提上，目标文献没有任何前提假设。当元数据完整时两侧都部分成立；元数据缺失时（>30% 文档）源文献方案失效，冲突实际消解为「目标文献覆盖源文献的失效域」——这个条件区分是第 07 讲「端间耦合」空白的直接证据 |
| 建立日期 | 2026-12-03 |

**样例 2（一页主题索引——注意三行纪律）**

| 字段 | 值 |
| --- | --- |
| 主题名 | 时效性约束的检索增强 |
| 主题标签 | 时效性检索 |
| 条目评语 | Freshness-Aware Retrieval：首个把生效日期写进检索打分的完整工作（待复现）；Wang et al. 2025：生成端引用对齐，处理同一问题的另一半；Survey on Temporal IR（**需核实**）：给出「文档时效」在传统 IR 中的定义谱系 |
| 共识三行 | ①「时间信息应进入检索或生成至少一端」已是共识；②打分融合与生成约束的收益量级相当（约 +5～8 点）；③评测集普遍假定元数据完整。 |
| 开放问题三行 | ①两端耦合（检索端与生成端联动）是否大于各自之和？②元数据缺失时如何降级？③「同一文档多次修订」的引用回溯谁在做？ |
| 状态 / 最近更新 | 活跃 / 2026-12-05 |

**样例 3（一次维护例程——多数例程应该这么朴素）**

| 字段 | 值 |
| --- | --- |
| 日期 | 2026-12-05（周五） |
| 清箱 / 修链 / 更索引 | 3 ／ 2 ／ 1 |
| 超时即停 | 勾选 |
| 遗留 | 两张待判决超过两周的条目（附标题），下周五优先处理 |

三张样例说明什么算「填得好」：样例 1 的 `说明` 里出现了「**成立条件**」——冲突关系只有写到条件层面才有张力价值；样例 2 的开放问题第二行「元数据缺失时如何降级」**后来变成了第 06 讲样例 2 论文的局限**——索引的开放问题三项就是在这样喂养选题。

## 4. 视图与交互设计

| 视图名 | 类型 | 配置要点 |
| --- | --- | --- |
| 某文献的全部关系（在 `08 文献关系` 上） | grid | 按 `源文献` 分组，用于条目详情页的「关联」区块 |
| 冲突对（同表） | grid | 过滤：`关系类型 = 冲突`——第 07 讲张力探针的原料 |
| 未连链条目（另一侧，`文献库` 上） | grid | 过滤：`关联关系` 为空 且 `阅读级别 ≥ 泛读` |
| 活跃主题（在 `08 主题索引` 上） | grid | 过滤：`状态 = 活跃`；按 `最近更新` 降序——本讲主工作视图 |
| 休眠待归档（同表） | grid | 过滤：`状态 = 活跃` 且 `最近更新 < 今天-90 天` |
| 开放问题池（同表） | grid | 按主题分组看 `开放问题三行`——选题会议的原料 |
| 例程坚持率（在 `08 维护日志` 上） | grid | 按周分组，看是否有缺周（此视图给第 23 讲周复盘消费） |

**记录详情页布局**：

- `08 文献关系`（分组样式，两列）：分组 1「两端」：源文献 / 目标文献 / 关系类型；分组 2「说明」：说明 / 建立人 / 建立日期。
- `08 主题索引`（分组样式，两列）：分组 1「定位」：主题名 / 主题标签 / 状态 / 最近更新；分组 2「内容」：条目评语 / 共识三行 / 开放问题三行（单列）；分组 3「关联」：关联文献 / 索引正文。

**表单**：新增表单视图 `连一条关系`，字段限定为 源文献 / 目标文献 / 关系类型 / 说明 四项——读完一篇文献顺手连链的动线。主题索引不设表单（它应该被「更索引」动作编辑，而不是被快速创建）。

## 5. 自动化设计

| 名称 | 触发器 | 条件 | 动作 | 防的坑 |
| --- | --- | --- | --- | --- |
| 周五 30 分钟例程 | `schedule weekly:5:17:00`（绑定 `08 维护日志`） | —— | `feishu_bot`（“本周 30 分钟：清箱、修链、更索引，超时即停”）+ `create_record`（建在绑定的这张表里——同表，合规用法；日期由系统字段「创建时间」自动带上） | 维护例程靠自觉必然断档 |
| 新条目须连链 | `record_created` on `文献库` | —— | `add_comment`（“请至少建立一条关系链接（上承/冲突/共享假设/部件复用）后再置为已审定”） | 文献越积越多、关系一条没有——「只囤不拆」的自动化防线 |
| 休眠主题提醒 | `schedule weekly:5:17:00`（绑定 `08 主题索引`） | —— | `run_agent`（查 `休眠待归档` 视图，对命中的主题记录逐条 `add_comment`：“90 天未更新：要么本周更一次索引，要么归档”） | 主题索引腐烂成僵尸页 |

> 「非空才留言」不写成条件——动作之间没有条件分支，留言由智能体的工具完成（视图为空时它自然什么都不做），因此这条自动化只配 `run_agent` 一个动作。

> 自动化的四条动作边界（动作作用范围限于触发记录或同库指定表、动作之间无分支、`notify` 须指定接收人、`field_equals` 会重复命中）见 `README.md` §3 与 `_系统能力现状.md` §2。

## 6. 智能体设计

### 站内智能体

**`跨条目提问机`（模式：`tools`）**

- 工具：`query_records`（按 `主题标签` 拉取相关条目与主题索引）+ `add_comment`。
- **出库提问的纪律**：给它的从来不是「我的知识库知道什么」，而是「这是主题索引与相关条目，请基于它们回答」。提示词要求它在回答中**对每个论断标注来源条目标题**，并列出「上下文未覆盖、需要我自己判断」的部分。
- 产出采用前，逐条回库核对，按第 04 讲挂 `复核记录`（`对象类型 = 段落主张`）。
- 系统提示词骨架：

```text
你是我的知识库检索助手。你只能基于我给你的上下文（主题索引与相关文献条目）回答，不得引入上下文之外的信息。

【任务】回答我的问题时：
1. 每个论断后标注来源条目标题；找不到来源的论断单独归入「上下文未覆盖」一节；
2. 如果上下文内部互相矛盾，把矛盾原样指出，不要替它们调和；
3. 回答的最后给出「本回答需要回库核对的事实点」清单。

【硬约束】
- 不允许使用「根据我的知识」这类表述；
- 不允许对来源条目做超出其文本的推论；
- 所有数字照抄上下文，禁止换算与四舍五入。
```

### 外部 MCP 工作流

1. **关系候选提名**：外部 Agent 读 `文献库` 新条目与既有条目，按「上承/冲突/共享假设/部件复用」提名关系候选（写入 `08 文献关系` 草稿、待审定），人确认后生效——**提名的不是关系，是候选**。
2. **索引保鲜扫描**：按 `开放问题三行` 的关键词检索近三个月新工作，把命中项写进主题索引评论，供「更索引」时使用。

### 红线（AI 只能给草稿）

- **`共识三行` 与 `开放问题三行` 必须人写**。索引是人的判断快照；AI 直填的索引没有人读过，等于没有。
- **`说明` 栏的条件必须人写**（「在哪个条件下结论相反」是这页最有价值的句子）。
- **关系候选的确认由人做**。AI 提名会把「引用关系」误当「上承」，需要人排除。

## 7. 与其他讲的接口

- **上游**：`文献库`（第 06 讲，`阅读级别 ≥ 泛读` 的条目才配拥有关系与索引）。
- **下游**：
  - 第 07 讲：`冲突对` 是张力探针的原料；主题的共识/开放问题直接进入综述的「尚未解决」段落。
  - 第 23 讲：主题索引页是一个模板（`模板库`）；`例程坚持率` 给周复盘消费。
  - 第 24 讲：主题是 `24 研究纲领` 的问题域候选。
  - 第 01 讲：开放问题三行是问题矩阵的二级输入（索引看自己的一亩地，矩阵看领域）。
- **单一事实来源**：**关系与主题索引只在本讲的三张表**。笔记软件里的散点笔记允许存在，但不能作为关系与索引的来源。

## 8. 分期实施与验收

### P0（纯配置，零代码）

1. 建三张表：`08 文献关系` / `08 主题索引` / `08 维护日志`。
2. 建视图：某文献的全部关系 / 冲突对（关系表）；活跃主题 / 休眠待归档 / 开放问题池（索引表）；例程坚持率（维护日志）；未连链条目（文献库上）。
3. 建表单视图 `连一条关系`。
4. 建三条自动化：周五 30 分钟例程 / 新条目须连链 / 休眠主题提醒。
5. 建站内智能体 `跨条目提问机`，提示词入 `提示词库`。
6. 词表对齐：`文献库.主题` 与 `08 主题索引.主题标签` 使用同一套选项（手工维护，P1 见第 8 节）。

### P1（少量增强）

| 需求 | 说明 | 建议落点 |
| --- | --- | --- |
| 空间级受控词表 | 主题词表目前靠手工对齐两个字段的选项 | 字段选项共享（`src/store.ts`）或词表表 + 查找引用 |
| 关系自动提名 | 现在是 MCP 提名 + 人工确认 | 智能体 `tools` 扩展（读两表、写候选） |
| 索引页模板化 | 新主题索引从模板一键生成 | `模板库`（第 23 讲）联动 |

### P2（可选）

- 「关系密度」仪表盘：按月看新链接数——它是「拆」与「囤」的比例计。
- 开放问题的生命周期追踪：一个问题从「开放问题池」→「问题矩阵」→「假设」→「论文」的完整路径回放（与第 24 讲联动）。

### 验收标准

1. `未连链条目` 视图中的泛读以上条目保持清零或每条有明确的无关系理由。
2. 每条 `08 文献关系` 记录的 `说明` 都能回答「在哪个条件下」。
3. 每个 `活跃` 主题都有完整的 条目评语 / 共识三行 / 开放问题三行，且三行纪律没有被破（没有第四行）。
4. `例程坚持率` 视图连续 4 周无缺周。
5. 抽查一次 `跨条目提问机` 的回答：所有论断带来源标注，「上下文未覆盖」一节非空（全知型回答说明它在编）。
6. `冲突对` 视图非空且其中的条目在第 07 讲的张力段落里被实际引用过。

## 9. 与原文的偏差说明

| 偏差 | 原文做法 | 本设计做法 | 理由 |
| --- | --- | --- | --- |
| 组织层复杂度 | 强调「组织永远服务取用」，批评目录完美主义 | **主动拒绝**提供二级分类目录字段：只留 `主题` 多选 + `状态` 三档 | 把误区三的防线设在系统层面——结构上不提供，就不会有人去整理 |
| 关系类别的落点 | 四类关系的概念教学 | `关系类型` 单选 + `冲突对` 等分用途视图 | 四类的价值在用途不同：冲突供综述、上承供引言、复用供实验——用视图把用途显性化 |
| 出库提问的形态 | 「带上下文提问」 | 提示词强制「标注来源 + 未覆盖清单 + 回库核对点」 | 没有这三条，带上下文和普通问答没有区别 |
| AI 直填的防线 | 列为误区二（纪律） | `共识三行`/`开放问题三行` 明文禁 AI + 出库论断挂 `复核记录` | 纪律需要两道机制：写入端的禁止与读出端的核对 |
| 维护例程 | 每周 30 分钟（习惯） | 周五定时消息 + 自动建日志 + 坚持率视图 | 30 分钟例程的成本极低、收益滞后，最容易断——需要三件套托住 |
