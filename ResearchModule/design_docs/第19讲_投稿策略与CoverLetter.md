# 第 19 讲 投稿策略与 Cover Letter：系统落地设计

> 来源：`../design_principle/第19讲_投稿策略与CoverLetter.pdf`
> 落地度：★★★★★（高） ｜ 依赖：第 17 / 18 讲 ｜ 主体分期：P0
> 主产物：三张表——`19 投稿目标`（候选池 + 三维评估）、`19 审稿人候选`（推荐与回避名单）、`19 投稿记录`（一次投稿一行，48 小时清单挂在上面）

## 1. 本讲方法要点

1. **投稿是匹配决策，不是质量赌博**。「本刊范围与来稿不符」这类匹配拒稿与质量问题无关，但同样烧掉半年。匹配可以用结构化方法优化，质量不能。
2. **三维评估：范围匹配度、读者匹配度、审稿周期与节奏**，每项 1–5 分，**乘积排序**。三维是相乘而非相加：**任何一项为 1（明显不达标），总分即归零，直接排除**。
3. **范围匹配的快速检验法**：不要只看期刊名称，去读它最近两年发表的论文——你的参考文献列表中至少应有 3–5 篇出自该刊/该会；再把自己论文的引言给编辑看，他能否在三句话内说出「这篇为什么属于我们」。
4. **周期数据的来源有优先级**：官方数字往往偏乐观；向近两年在该刊发表过论文的同行打听**实际周期**（从投稿到一审意见）更可靠。更根本的一条：**记录自己每次投稿的时间线（投稿、送审、一审意见、录用）——三五次之后，你就有了属于自己方向的私有数据库，比任何公开统计都可靠**。
5. **会议与期刊的节奏逻辑不同**：会议是「定点班车」，错过一班等半年到一年，但时间线确定；期刊是「随到随审」，时间线不确定且修改轮次多。常用策略是「会议优先、期刊兜底」的梯队。
6. **候选池而非一次性决策**：三维评估表应维护成候选池，每次投稿前更新周期数据与目标近两年的发文方向。
7. **Cover Letter 回答的唯一问题**：「为什么这篇论文值得占用本刊三位审稿人的时间？」推荐四段结构——**问题 → 方法 → 结果 → 适配**，全文不超过一页，篇幅 300–400 词。
8. **三个写作纪律**：① 数字必须与摘要逐字一致；② 「适配」段必须引用该刊近期真实发表的同类论文——**写不出来说明范围匹配度存疑**；③ 全文不得出现「重大突破」「国际领先」之类的自我评价——**贡献由数字说话**。
9. **它也不是第二份摘要**：摘要回答「论文做了什么」，Cover Letter 回答「为什么适合这里」；两者信息有重叠，但视角不同。
10. **desk rejection 四种原因**：范围不符、贡献表述不清、语言质量差、格式严重违规。四段结构正对前两种，后两种由第 17、18 讲的流水线与本讲末尾的检查清单拦截。
11. **推荐审稿人策略**：推荐**同细分方向活跃、无利益冲突、真实可查**的学者 3–5 人（参考文献中的中青年作者优先，资深大佬通常太忙而拒审）；不推荐合作者、同单位同事、近三年共同署名者；直接竞争者中可能恶意拖延者列入「需回避」。
12. **一条灰线不要踩**：推荐审稿人必须是**真实存在的独立学者，用真实单位邮箱**。虚构审稿人、推荐「影子账号」属于学术不端，后果远重于一次拒稿。单位邮箱优先于通用邮箱——编辑验证身份的成本更低，采纳率更高。
13. **48 小时检查清单六项**：匿名性（含 PDF 元数据作者字段清空）、格式合规、数字一致性、引用完整性、材料齐备（含伦理声明、利益冲突声明、代码链接）、最终通读（**出声朗读摘要与引言，打印版翻阅图表**）。补充材料同样要检查——审稿人对补充材料的宽容度更低，因为它是「自愿提供」的。
14. **最后一项纪律：提前 24 小时提交**。投稿系统在截止前数小时崩溃是常态而非意外。提交后三个动作：确认收稿回执与稿件编号；把投稿日期、目标、编号记入项目管理表（**它将是你计算「实际一审周期」的原始数据**）；停止反复打开投稿系统。
15. **提交后发现重大错误（如关键数据错误），立即联系编辑**争取在送审前撤回修改——带病投稿一旦被接收，事后撤稿的代价远大于撤回重投。

| 参考文献命中数自动统计 | 现在人工点数 | 脚本（解析 .bib 与目标刊近两年目录） | P1 |

**不建议系统化的部分**：

- **Cover Letter 的语气与个人叙事**不进系统。它是编辑五分钟内形成第一印象的文本，句子的取舍属于人；系统只保证三件事：数字与摘要一致、适配段有真实文献、没有自我评价词。
- **与编辑的邮件往来**不进系统。往来记录的价值在于事后查证，而它天然存在于邮箱里；复制进系统只会多一份可能过期的副本。
- **「与导师或合作者当面过一遍三维评估」**不做成会签流程。原文明确说这是「经验无法被清单完全替代的部分」——它的价值恰在于非正式的讨论，不在留痕。
- **审稿人候选名单的日常积累**不做自动抓取。原文说的是「平时维护一个持续更新的候选笔记」，系统提供这张表就是它的落地；自动抓取会把「你认识谁、谁可能答应」这个判断机械化为引用数排序。

**关系与公式**：

- `19 投稿记录.稿件` → `稿件`（第 17 讲）：一次投稿只对应一篇稿件的一个版本。
- `19 投稿记录.目标` → `19 投稿目标`：**一次投稿只投一个目标**，转投就是新的一条记录——这样投稿历史天然形成时间线。
- `19 审稿人候选` ↔ `19 投稿记录`：同一位学者在多轮投稿中可以「推荐」也可以「回避」，关系由投稿记录这一侧指定。
- **不使用跨表聚合**：「任一维为 1 即排除」用视图表达而不用公式——排除权在人，视图只是把可疑项摆出来。

### 3.2 记录样例

**样例 1（`19 投稿目标` 的三行——对应原文的表 19.1）**

| 名称 | 范围匹配 | 读者匹配 | 周期评分 | 综合排序 | 参考文献命中数 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 期刊 A | 5 | 4 | 2 | 40 | 5 | 候选 |
| 期刊 B | 4 | 5 | 4 | 80 | 4 | 选定 |
| 会议 C | 3 | 4 | 5 | 60 | 3 | 候选 |

记录写法：**期刊 A 的范围匹配给了 5 分，却因周期评分只有 2 分被乘积拉低**——这正是「相乘而非相加」的直观体现；三行的 `参考文献命中数` 都 ≥ 3，说明三个目标都经过了范围检验。若某行为 0，它会在 `范围存疑` 视图里等着被排除。

**样例 2（`19 投稿记录` 的一行——已提交，48 小时检查六项齐备）**

| 字段 | 值 |
| --- | --- |
| 稿件 / 目标 | 检索增强长文档问答 ／ 期刊 B |
| 投稿日期 | 2026-03-12 |
| 材料清单 | Cover Letter、推荐审稿人名单、补充材料、伦理声明、利益冲突声明、数据与代码可用性声明、匿名版正文（七项全中） |
| 48 小时检查 | 匿名性、格式合规、数字一致性、引用完整性、材料齐备、最终通读（六项全中） |
| 提前 24 小时提交 | ✅（截止 03-13 23:59，实际 03-12 提交） |
| 提交后下载终稿复核 | ✅ |
| 状态 | 已提交 |

**样例 3（一次「经验回填」的闭环）**

三个月后状态改为 `一审`，收到一审意见后：

1. 把 `实际一审周期（天）` 填为 95（投稿日到一审意见日的实际天数）；
2. 勾选 `经验回填`；
3. 用按钮把 95 天折算的月数写回 `19 投稿目标.实测周期（月）`——**官方数字是 3 个月，实测是 3.2 个月，落差进入下一轮候选池评估**。

这条闭环的价值在第三次投稿时显现：`周期超限` 视图不再依赖打听来的模糊数字，而是你自己的时间线。

## 4. 视图与交互设计

**主视图与筛选口径**：

- `候选池`是决策主视图：按 `综合排序` 降序，一眼看到三个候选的相对位置；`排除原因` 列（隐藏字段按需展开）是复盘时最有价值的一列。
- 四个闸门视图各管一条纪律：`一票否决`（任一维为 1 却还留在候选池）、`范围存疑`（命中数不足）、`周期超限`（超出倒推上限）、`红线警告`（审稿人未核验真实性）。**这四条纪律的共同点是「当时看起来都没问题」**——它们只有在视图里才可见。

**日历与看板怎么配**：

- `截稿日历`绑定 `截稿日`：会议的「定点班车」性质靠日历呈现最直观；期刊目标没有截稿日，不进日历。
- `在审`看板按 `状态` 分列：从 `准备中` 到 `接收/拒稿/转投`，一条投稿的完整生命周期。**看板的总宽度即你的投稿吞吐量**——同时压在「一审」及以后的稿件超过三篇时，说明该考虑降低新投稿节奏。

**记录详情页布局**：

- `19 投稿目标`（分组样式，两列）：分组 1「三维」：名称 / 类型 / 范围匹配 / 读者匹配 / 周期评分 / 综合排序；分组 2「周期」：官方周期 / 实测周期 / 可接受周期上限 / 截稿日；分组 3「判定」：参考文献命中数 / 结论 / 排除原因 / 评估日期。
- `19 审稿人候选`（分组样式，两列）：分组 1「身份」：姓名 / 单位 / 邮箱 / 方向 / 代表作 / 来源；分组 2「可信度」：被引频次档位 / 利益冲突 / 关系类型 / 回避原因 / 真实性核验；分组 3「使用记录」：最近接触 / 可推荐次数 / 备注。
- `19 投稿记录`（分组样式，两列）：分组 1「本次投稿」：稿件 / 目标 / 投稿日期 / Cover Letter；分组 2「名单」：推荐审稿人 / 回避名单；分组 3「清单」：材料清单 / 48 小时检查 / 提前 24 小时提交 / 提交后下载终稿复核；分组 4「结果」：状态 / 实际一审周期 / 经验回填。

**表单**：

- `评估一个目标`：字段限定为 名称 / 类型 / 范围匹配 / 读者匹配 / 周期评分 / 参考文献命中数 / 可接受周期上限——**先评分再谈感情**。
- `登记一位候选人`：字段限定为 姓名 / 单位 / 邮箱 / 方向 / 代表作 / 来源 / 关系类型——真实性核验与利益冲突在录入后单独确认，因为它们是判断题。
- `发一次投稿`：字段限定为 稿件 / 目标 / 投稿日期——其余在提交前后逐项补齐。

**文档**：《Cover Letter》用系统内文档承载，`19 投稿记录.Cover Letter` 做挂靠（label 用「投稿版 / 修改版」）。文档的历史版本自动归档正好对应「每更换一次投稿目标，按新目标的政策重新核对」这个动作——改前的版本可回溯。

## 5. 自动化设计

| 名称 | 触发器 | 条件 | 动作 | 防的坑 |
| --- | --- | --- | --- | --- |
| 截稿临近 | `schedule daily:09:00` | —— | `run_agent`（查 `截稿日` 在未来 7 天内的记录）→ `feishu_bot`（推送目标名与倒计时） | 会议是「定点班车」，错过一班等半年到一年 |
| 材料不齐不放行 | `field_equals`（`状态` = 已提交） | `材料清单` 未含「匿名版正文」或 `48 小时检查` 缺项 | `add_comment`（列出缺项；并提示「补充材料的检查标准比正文更严，因为它是自愿提供的」） | 提交按钮点下去才发现材料缺一项 |
| 截稿前 24 小时提醒 | `schedule daily:09:00` | 截稿日 = 明天 且 `状态` = 准备中 | `feishu_bot`（“投稿系统在截止前数小时崩溃是常态而非意外：提前 24 小时提交”） | 卡点提交 |

**关于「截稿前 24 小时提醒」的落地方式**：现有 `run_agent` 可以读表并生成摘要文本，但它不能比对「明天」这种相对日期——这条在 P0 用「`截稿日` 在未来 2 天内的所有记录」做粗过滤 + 每日推送整表倒计时实现（宁可多推一天，不可漏推一天）；P1 建议给 `schedule` 条件加「相对日期比较」（落点 `src/store.ts` 的触发器条件求值处）。

## 6. 智能体设计

### 站内智能体

**`适配段起草员`（模式：`prompt`）**

- 输入（用户提供）：论文摘要 / 一句话贡献、目标刊名称、**目标刊最近两年的同类论文清单**（自己整理的真实文献）。
- 输出：Cover Letter 第四段「适配」的初稿 2–3 个版本，以及一个「你提供的文献与本文的契合点」清单。
- 系统提示词骨架（存进 `提示词库`）：

```text
你是 Cover Letter 适配段的起草助手。我会给你：本文的摘要与一句话贡献、目标刊名称、
该刊最近两年同类论文的清单（作者+标题+一句话内容）。

【任务】起草 2–3 个版本的「适配」段，每个版本不超过 80 词：
- 结合清单里的真实论文，说明读者群契合点；
- 少用形容词，多用事实与具体方向名；
- 不使用「重大突破」「国际领先」之类的自我评价；
- 结尾一句确认：未一稿多投、所有作者知情同意。

【硬约束】
- 只能引用我提供的文献清单，不得自行生成或补全任何参考文献条目；
- 清单里没有的论文一律不允许出现——写不出契合点就直接说「清单不足以支撑适配段」；
- 不允许复述摘要内容：这一段回答的是「为什么适合这里」，不是「论文做了什么」。
```

**`三维评估复核员`（模式：`tools`）——可选**

- 工具：`query_records`（读 `19 投稿目标`）。
- 用途：找出「评分与证据不匹配」的目标——如 `范围匹配 ≥ 4` 但 `参考文献命中数 < 3`；`结论 = 选定` 但存在任一维为 1。
- **明确禁止**：由 AI 给三个维度打分。范围与读者的判断是选题品味的一部分，AI 只能校验「证据是否支持你打的分数」。

### 外部 MCP 工作流

1. **参考文献命中数统计（P1）**：外部 Agent 解析稿件的 .bib 文件，与目标刊/会近两年的论文目录比对，输出「命中几篇、分别是哪几篇」，写回 `参考文献命中数` 与一条评论。这是把「至少 3 篇」从人工点数变成可复现的检查。
2. **格式合规批量预检（P1，与第 22 讲共用）**：按目标刊的作者指南核查模板版本、页数上限、参考文献格式、图表分辨率，异常逐条建 `核查清单` 记录。
3. **投稿时间线导出（P2）**：把 `19 投稿记录` 按年份导出为个人周期统计（各刊实测中位数），代替打听——把自己的历史变成数据库。

### 红线（AI 只能给草稿）

- **三维评分由人打**。AI 可以帮你找证据（命中文献、历史周期），但范围与读者的判断不进 AI 的输出。
- **适配段引用的文献必须是真实文献**。提示词里写死了「只能引用我提供的清单」——这条与第 20 讲的引用核验是同一条红线在 Cover Letter 场景的实例。
- **推荐审稿人的真实性核验由人做**。`真实性核验` 复选框勾不勾是人的判断；AI 可以帮助核对单位邮箱格式，但「这位学者是否真实存在、是否独立」必须你亲自确认。
- **48 小时清单的「最终通读」由人做**：出声朗读摘要与引言、打印版翻阅图表——屏幕上看不出的排版问题，纸上一眼可见。

## 7. 与其他讲的接口

- **上游**：
  - `稿件`（第 17 讲）：`19 投稿记录.稿件` 指向它；投稿版冻结时写 `稿件.冻结时间`。
  - `18 图表台账`：格式合规检查的第一站是图表格式与分辨率。
  - `文献库`（第 06 讲）：`参考文献命中数` 的原始数据来自这里。
- **下游**：
  - 第 21 讲：`21 审稿意见.投稿记录` 指向本表；`21 转投决策.原投稿记录` 也指向本表。
  - 第 22 讲：投稿前 48 小时清单的第 1–5 项与五区二十五条互补落地——**清单化在这里，完整判据在第 22 讲**。
  - 第 23 讲：`23 年度回顾.导出范围` 包含「投稿与审稿记录」——`19 投稿记录` 是年度回顾的原料之一。
- **单一事实来源**：**投稿历史只在本表**。Cover Letter 与推荐名单是它的附件（文档与关联记录）；同一个目标期刊的评估结论不允许多处维护。

## 8. 分期实施与验收

### P0（纯配置，零代码）

1. 建三张表：`19 投稿目标` / `19 审稿人候选` / `19 投稿记录`。
2. 建视图：目标的 候选池 / 一票否决 / 范围存疑 / 周期超限 / 截稿日历；审稿人的 可推荐 / 红线警告 / 需回避；投稿记录的 准备中 / 待回填周期 / 在审。
3. 建三个表单视图：`评估一个目标` / `登记一位候选人` / `发一次投稿`。
4. 建三条自动化：截稿临近 / 材料不齐不放行 / 截稿前 24 小时提醒。
5. 建站内智能体 `适配段起草员`（必建）与 `三维评估复核员`（可选）；提示词入 `提示词库`。
6. 建文档模板《Cover Letter》（四段结构 + 三个写作纪律写在模板头部注释里）。
7. 打通接口：`19 投稿记录.稿件` → `稿件`；`19 投稿记录.目标` → `19 投稿目标`；`19 投稿记录.推荐审稿人 / 回避名单` → `19 审稿人候选`。

### P1（少量增强）

| 需求 | 说明 | 建议落点 |
| --- | --- | --- |
| 参考文献命中数自动统计 | 现在人工点数 | 脚本（解析 .bib × 目标刊近两年目录） |
| `综合排序`公式化 | 现在人填乘积 | 公式引擎（三个数值字段相乘） |
| `schedule` 支持相对日期比较 | 24 小时提醒现在的粗过滤 | `src/store.ts` 触发器条件求值 |
| 周期统计报表 | 按目标汇总 `实际一审周期` 的中位数与分布 | 仪表盘（bar / line） |

### P2（可选）

- 把三篇以内的投稿记录导出为「个人周期数据库」的年度快照——投稿满五次之后，它比任何公开统计都可靠。
- 目标刊近两年论文目录的半自动采集（外部脚本抓取目录页），仍由人确认入库。
- `19 审稿人候选`与 `文献库` 的关联：被推荐学者的代表作直接指向库内条目。

### 验收标准

1. `一票否决` 视图为空：候选池里没有任一维为 1 的目标。
2. `范围存疑` 视图为空：每个保留在候选池的目标，`参考文献命中数 ≥ 3`。
3. `红线警告` 视图为空：所有进入推荐名单的学者都完成了真实性核验。
4. 每次 `状态 = 已提交` 的投稿记录，`材料清单` 与 `48 小时检查` 均无缺项，且 `提前 24 小时提交` 已勾选。
5. 一审意见到达后 7 天内，`实际一审周期（天）` 已填写且 `经验回填` 已勾选。
6. 抽查一份 Cover Letter：三个写作纪律可复现——数字与摘要逐字一致、适配段引用的文献真实存在、全文无自我评价词。

## 9. 与原文的偏差说明

| 偏差 | 原文做法 | 本设计做法 | 理由 |
| --- | --- | --- | --- |
| 乘积排序 | 「每项 1–5 分，乘积排序」 | `综合排序` 是人填的数字（P1 才公式化） | 保留「人做乘积排序时会停下来想一想」这一步——**三个维度里最弱的那一项往往才是决策依据**，自动算出的乘积会让人跳过这个判断 |
| 收录命中数 | 「参考文献列表里至少应有 3–5 篇」 | `参考文献命中数` 数字 + `范围存疑` 视图，阈值取 3 | 原文给的是一个区间；系统需要一个可判的阈值。取区间下限 3 作为闸门，4–5 的目标在报告中另行说明 |
| 周期信息来源 | 「向同行打听实际周期」 | 保留 `实测周期` 字段，另加「自己记录时间线」的闭环（`实际一审周期` + `经验回填`） | 原文把「记录自己的时间线」列为比公开统计更可靠的信息源；系统恰好天然擅长这件事——它把这条建议从「值得做的事」变成「顺手就完成的事」 |
| 审稿人候选笔记 | 「平时维护一个持续更新的笔记」 | `19 审稿人候选` 表 | 笔记的失败模式是「投稿时找不到」；表 + `可推荐` 视图让名单随时可检索。`真实性核验` 复选框把红线写进字段——虚构审稿人是全书中少数几条「一次即不可逆」的红线之一 |
| 48 小时清单 | 六项人工动作 | `材料清单` + `48 小时检查` 两个多选 + `材料不齐不放行` 自动化 | 与第 18 讲的同一逻辑：一串人工动作的失败模式是「漏做一项」；拆成字段后，缺项在提交前就能被自动化点出来 |
| 「适配段写不出来说明范围匹配度存疑」 | 一句话判断 | 不做成字段；写进 `适配段起草员` 的硬约束（清单不足时直接报告「不足以支撑适配段」） | 这是本讲最锋利的一条判断，但它的产物是一个「写不出来」的否定信号——做成字段会诱导人硬写出一个空泛的适配段，而原文要的恰恰相反 |
| 投稿后的三个动作 | 「确认回执 / 记入项目管理表 / 停止盯系统」 | 前两个落成字段（`状态`、`投稿日期`）；第三个不进系统 | 「停止反复打开投稿系统」是纪律不是数据；把它做成打卡字段反而增加了盯系统的理由 |
