# 第 12 讲 可复现实验框架：系统落地设计

> 来源：`../design_principle/第12讲_可复现实验框架.pdf`
> 落地度：★★★★★（高） ｜ 依赖：第 10 讲 ｜ 主体分期：P0
> 主产物：共享表 `配置台账`（一行 = 一个实验的一份配置，文件名即实验编号）+ 表 `12 环境指纹`（一行 = 一次实际运行环境）+ 表 `12 种子清单`（四层随机源的排查记录）+ 表 `12 复现自查`（一行 = 一次自查运行）

## 1. 本讲方法要点

1. **可复现性的检验标准只有一条**：三个月后的你，在一台干净的机器上，只凭仓库和配置文件，能否把论文里的数字重跑出来。它不是美德，是效率——不能复现自己工作的人，永远在重跑实验。
2. **种子要四层全覆盖**：数值库层（Python `random` 与 NumPy 各自的生成器）→ 框架层（框架种子、CUDA 种子、DataLoader worker 的 `worker_init_fn`、打乱用的 generator）→ 数据顺序层（shuffle、随机裁剪翻转等增强、分布式分片顺序）→ 硬件算子层（部分 CUDA 算子默认非确定性，需开确定性开关，有性能代价）。漏一层就有漂移。
3. **所有种子收敛到一个配置项**。代码库中禁止散落的魔法数字种子；每个实验的种子写进配置文件，结果表能反查到种子值。
4. **环境锁定分两层、由内到外**：第一层依赖版本锁定（精确版本 `torch==2.1.0` 而非 `>=`；conda 快照注意平台相关字段）；第二层容器镜像（把操作系统、系统库、CUDA 工具链一并固定）。最低成本的实践是「容器内复现一次」——换一台机器从镜像重建、按配置重跑，确认结果落在种子噪声内。
5. **除事前锁定，还要事后记录**：每次实验启动时把实际环境（框架版本、CUDA、GPU 型号、驱动版本、git 提交哈希）写进日志头部。锁定管「将来能重建」，记录管「当时是什么」，两者缺一，三个月后排查漂移时就没有比对基准。
6. **锁定要分层，不走极端**：主结果表与消融表对应的实验走完整锁定流程，预研实验只要求种子固定与依赖清单。**把成本花在会被引用的数字上**。
7. **一个实验一个配置文件，文件名即实验编号**，一切可变因素（模型参数、数据路径、超参、种子、硬件要求）全进配置，代码中不出现硬编码的实验常数。**配置必须先于实验运行存在**——跑完凭记忆补写的配置是口述历史，不是文档。
8. **配置目录天然是实验台账**，且与第 9 讲的假设登记表关联（配置里的 `hypothesis` 字段），形成「假设 → 实验 → 结果」的完整链条。
9. **复现性自查脚本不需要聪明，只需要诚实**：配置完整性检查、种子播种、框架版本比对，以及终极提醒——同一配置重跑两次，结果文件应当逐字节一致。脚本随项目演进，每踩到一个新坑就加一条检查；它同时是项目交接的最佳文档。

| 能力点 | 落地形态 | 依托的现有能力 | 优先级 |

| 配置先于运行 | `配置先于运行` 复选框 + `配置缺失` 告警视图 + 自动化 | 复选框、过滤、`record_created` + `add_comment` | P0 |

| 自查脚本本体与容器化 | **系统外**：脚本在仓库里跑，系统只收结论 | —— | P0（文档约定） |
| YAML 与台账一致性校验 | MCP 工具 `check_config_ledger`：扫描仓库 YAML 目录，与 `配置台账` 对账 | MCP 工具 | P1（已落地） |
| 训练脚本自动回写环境指纹 | 从日志头部解析环境字段写入 `12 环境指纹` | MCP / 脚本 | P1 |

**不建议系统化的部分**：

- **容器化、CI、脚本执行本身**。系统不托管 Dockerfile，也不跑训练。系统承载的是「哪些实验走过完整锁定」「每个实验的配置与种子是多少」「当时的实际环境是什么」这三个审计问题。
- **确定性算子的性能取舍**。开不开、哪个实验开，需要在准确性与排队时间之间做判断，系统只登记 `确定性算子` 的最终选择。
- **调参探索与预研实验的完整性**。原文明确说锁定有成本、不要走极端；系统用 `是否主结果` 一个开关把这个边界钉住，不做更细的强制。

## 3. 数据模型设计

### 3.1 表结构

空间：`科研方法`。表：`配置台账`（共享表，第 10 / 15 讲共用）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 实验编号 | 自动编号（前缀 `exp-`） | **YAML 文件名即用它**：`exp-017.yaml` |
| 假设 | 关联 → `假设登记`（单值） | 对应配置里的 `hypothesis: H-01` |
| 一句话目的 | 文本 | 如「检索增强 vs 截断的对照」 |
| 配置文件 | 附件 | YAML 原文，便于直接查看与比对 |
| 配置文件路径 | 文本 | 仓库里的相对路径 |
| seed | 数字 | **全部随机源共用这一个字段** |
| 关键超参 | 多行文本 | YAML 片段：模型、数据、训练、评测四节的关键项 |
| 配置先于运行 | 复选框 | 勾选 = 该配置文件在实验运行前已存在 |
| 是否主结果 | 复选框 | 主结果表与消融表对应的实验走完整环境锁定 |
| 环境指纹 | 关联 → `12 环境指纹`（单值） | —— |
| 依赖锁定方式 | 单选 | 精确版本 requirements / conda 快照 / 容器镜像 / 无 |
| 确定性算子 | 单选 | 已开启 / 未开启 / 不适用 |
| 创建时间 | 创建时间（系统） | 「配置先于运行」的客观佐证 |
| 关联实验记录 | 关联 → `实验记录`（多值） | 一次配置对应 N 次运行 |

表：`12 环境指纹`（一行 = 一次实际运行环境；内容取自被写入日志头部的那份）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 实验编号 | 关联 → `配置台账`（单值） | —— |
| 日期 | 日期 | 运行日期，不是登记日期 |
| 框架版本 | 文本 | 如 `torch 2.1.0+cu121` |
| CUDA | 文本 | 如 `12.1` |
| GPU 型号 | 文本 | 如 `A100 80G` |
| 驱动版本 | 文本 | 如 `535.104.05` |
| git 提交哈希 | 文本 | 短哈希即可 |
| 容器镜像 | 文本 | 镜像名 + tag / digest |
| 机器标识 | 文本 | 开发机 / 集群名 / 云实例类型 |
| 依赖清单 | 附件 | `conda env export` 或冻结 requirements |
| 写入日志头部 | 复选框 | 确认训练脚本已把本行内容写入日志头部 |

表：`12 种子清单`（一行 = 一个随机源；轻量，全项目共用一份）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 层级 | 单选 | 数值库 / 框架 / 数据顺序 / 硬件算子 |
| 位置 | 文本 | 文件:行 |
| 随机源描述 | 文本 | 如「DataLoader worker 的 worker_init_fn」「随机裁剪与翻转」 |
| 是否可控 | 单选 | 已固定 / 不可控已记录 / 漏了 |
| 处置 | 多行文本 | 怎么固定的，或为什么选择不固定 |
| 检查日期 | 日期 | —— |

表：`12 复现自查`（一行 = 一次自查运行）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 日期 | 日期 | —— |
| 范围 | 单选 | 主结果表 / 消融表 / 预研实验 |
| 检查项 | 多选 | 种子全覆盖 / 确定性算子重跑一致 / 依赖精确锁定 / 环境快照导出 / 每实验独立配置 / 干净机器重跑通过 |
| 结论 | 单选 | 通过 / 失败 / 待办 |
| 失败说明 | 多行文本 | 哪一项没过、现象是什么 |
| 自查脚本 | 超链接 | 或者附件形式放脚本输出 |
| 检查人 | 成员 | —— |

**关系与公式**：

- `假设登记` → `配置台账` → `实验记录`：一条假设 N 份配置，一份配置 N 次运行。这是全书最锋利的一条证据链。
- `配置台账.环境指纹` → `12 环境指纹`：单值关联，因为一次配置在一次环境里跑；换环境重跑就新增一条指纹记录并在配置里改指向。
- `10 实验矩阵.关联配置` → `配置台账`（多值）：一行矩阵可以对应多份配置（如不同种子档）。
- **不使用跨表聚合**：本讲不涉及。

## 4. 视图与交互设计

| 视图名 | 类型 | 配置要点 |
| --- | --- | --- |
| 主结果实验（`配置台账`） | grid | 过滤：`是否主结果` 勾选；列取 实验编号 / 假设 / seed / 依赖锁定方式 / 环境指纹 —— 一次看清哪些数字承担了论文主结论 |
| 配置缺失（`配置台账`） | grid | 过滤：`配置文件` 为空；颜色规则：红色——**「配置先于运行」原则的告警视图** |
| 按假设归档（`配置台账`） | grid | 按 `假设` 分组 |
| 未走完整锁定（`配置台账`） | grid | 过滤：`是否主结果` 勾选 且 `依赖锁定方式 ≠ 容器镜像`——分层管理的边界提示，不是错误 |
| 漂移排查（`12 环境指纹`） | grid | 按 `GPU 型号` 与 `框架版本` 分组——三个月后查漂移先看它 |
| 漏网点（`12 种子清单`） | grid | 过滤：`是否可控 = 漏了`——「换一台机器跑出 1.5 个点差异」的常见成因清单 |
| 未通过（`12 复现自查`） | grid | 过滤：`结论 ≠ 通过` |
| 干净机器复现（`12 复现自查`） | grid | 过滤：`检查项` 含「干净机器重跑通过」——这条是验收的核心证据 |

**记录详情页布局**：

- `配置台账`（分组样式，两列）：分组 1「身份」：实验编号 / 假设 / 一句话目的 / 配置文件 / 配置文件路径；分组 2「可复现要素」：seed / 关键超参 / 配置先于运行 / 是否主结果 / 依赖锁定方式 / 确定性算子；分组 3「关联」：环境指纹 / 关联实验记录 / 创建时间。
- `12 环境指纹`（分组样式，两列）：分组 1「版本」：实验编号 / 日期 / 框架版本 / CUDA / 依赖清单；分组 2「硬件」：GPU 型号 / 驱动版本 / 机器标识 / 容器镜像 / git 提交哈希 / 写入日志头部。

**表单**：

- `登记一份配置`：字段限定为 假设 / 一句话目的 / seed / 关键超参 / 配置文件 —— 建配置时快速铺行。
- `记一次环境`：字段限定为 实验编号 / 日期 / 框架版本 / CUDA / GPU 型号 / git 提交哈希 / 容器镜像 —— 换机器重跑时当场记，别等回头补。

**仪表盘**（可选）：`复现健康度`——count（主结果实验数 / 无配置实验数 / 未通过自查数）、pie（依赖锁定方式的分布）。

## 5. 自动化设计

| 名称 | 触发器 | 条件 | 动作 | 防的坑 |
| --- | --- | --- | --- | --- |
| 配置先于运行 | `record_created` on `配置台账` | `配置先于运行` 未勾选 | `add_comment`（“配置必须先于实验运行存在；跑完才补写的不是配置，是口述历史”） | 事后回忆着补配置 |
| 种子缺一即告警 | `record_created` on `配置台账` | `seed` 为空 | `notify` + `add_comment`（“种子要四层全覆盖：数值库 / 框架 / 数据顺序 / 硬件算子——清单见 `12 种子清单`”） | 只设了一个 `seed=42` 就以为万事大吉 |
| 主结果实验要指纹 | `field_equals`（`是否主结果` = 勾选）→ 条件 `环境指纹` 为空 | —— | `add_comment`（“主结果实验需完整环境锁定：请补环境指纹并确认已写入日志头部”） | 主结果的数字没有环境出处 |
| 自查不通过即留痕 | `field_equals`（`12 复现自查.结论` = 失败） | —— | `add_comment`（“失败项写进失败说明，并在修复后保留这条记录——下一轮自查要能看出它被修过”） | 失败的复现检查被静默覆盖 |

**为什么本讲的自动化可以少**：复现性的执行发生在仓库里（脚本、镜像、配置），系统这一侧只做台账与告警。自动化的价值在于把「配置缺失」「seed 缺失」这两类结构性漏洞在**登记那一刻**就顶回去。

> 自动化的四条动作边界（动作作用范围限于触发记录或同库指定表、动作之间无分支、`notify` 须指定接收人、`field_equals` 会重复命中）见 `README.md` §3 与 `_系统能力现状.md` §2。

## 6. 智能体设计

### 站内智能体

**`配置审查员`（模式：`prompt`）**

- 输入（用户提供）：一份 YAML 配置全文，以及项目里随机性出现在哪些文件的信息（可选）。
- 输出：修订建议清单，四类问题——① 有硬编码的实验常数没进配置；② seed 不是一个单点（出现了第二个种子字段）；③ 数据增强的随机性没有对应开关；④ 缺配置节（model / data / training / eval）。
- 系统提示词骨架：

```text
你是可复现性审查员。输入是一份实验配置文件（YAML）。

【任务】逐条检查并输出问题清单：
1. 有没有硬编码的实验常数没进配置（如代码里写死的 lr、batch_size、路径）；
2. 种子是不是收敛到唯一一个字段，有没有出现第二个种子来源；
3. 数据增强（裁剪、翻转、shuffle）的随机性是否在配置里有对应条目；
4. 四个必需节（model / data / training / eval）是否齐备。

【硬约束】
- 只输出问题与修订建议，不替我改字段值；
- 不确定的地方标「待确认」，不要猜；
- 不允许把「配置写得完整」等同于「实验可复现」——确定性开关与 worker 种子只有在代码侧确认后才算数。
```

### 外部 MCP 工作流

1. **YAML 目录与台账对账（P1，已落地为 MCP 工具 `check_config_ledger`）**：外部 Agent 调工具，传仓库根目录（`root`，本机路径）或读好的文件清单（`files`，仓库不在本机时用），工具列 `配置台账` 的全部 `实验编号` 与 `配置文件路径`，扫描仓库 `configs/` 目录，输出三张清单——仓库里有但台账没有的（漏登记）、台账有但仓库里没有的（幽灵配置）、两边都有但 `seed` 不一致的（静默漂移）。另附三列诊断：seed 只有一边填（`seedIncomplete`）、台账路径与仓库实际路径不一致（`pathMismatch`）、配置自身告警（种子多来源、字段名不合口径、没写 `experiment_id`）。工具只读不写；编号比对把 `exp-1` 与 `exp-001` 视为同一编号（自动编号不补零），`experiment_id` 与文件名不一致时以文件名为准并告警。仓库侧因此有一条硬约定：**一个实验一个 YAML，文件名即实验编号**。
2. **环境指纹批量登记（P1）**：从各实验的日志头部解析框架版本、CUDA、GPU 型号、驱动版本与提交哈希，用 `create_record` 批量写入 `12 环境指纹`，人抽查后确认。
3. **生成 YAML 骨架**：按 `配置台账` 的一行与 `10 实验矩阵` 的对应单元，起草配置文件骨架（含 `experiment_id` 与 `hypothesis` 两行），人补超参后入仓库。

### 红线（AI 只能给草稿）

- **`seed` 的值由人定并写进配置**。AI 不得给出「建议种子 42」这类看似无害的默认值——它会让两批实验悄悄共用同一个种子。
- **`确定性算子` 的取舍由人做**。开与不开是性能与准确性的权衡，AI 只能列出差异。
- **`12 复现自查` 的 `结论` 由人填**。自查脚本的输出是证据，判定必须由人做；这与第 22 讲「不能用 AI 判通过/不通过」是同一条纪律。

## 7. 与其他讲的接口

- **上游**：`假设登记`（配置里的 `hypothesis` 字段）；`10 实验矩阵`（一行矩阵 → 一份或多份配置，经 `关联配置` 字段连接；MVE 是第一份配置）。
- **下游**：
  - 第 15 讲：`实验记录.配置` 指向本表——一次配置 N 次运行，六字段里的「配置哈希」在这里有唯一出处。
  - 第 14 讲：数据版本进环境指纹（`12 环境指纹` 的 `依赖清单` 与数据哈希在 `14 数据资产` 的 `哈希` 字段互认）。
  - 第 18 讲：图表的每个数字都能沿 `图表台账.数据来源 → 实验记录 → 配置台账` 追到种子与环境。
  - 第 22 讲：核查清单的统计区会交叉验证「主结果是否走过完整锁定」。
- **单一事实来源**：**配置只在本表一份**。代码仓库里的 YAML 是可执行副本，台账是索引与审计口径；两者不一致时以台账为准并修正仓库（或反之）——但必须显式修正一处，不允许长期并存两个版本。

## 9. 与原文的偏差说明

| 偏差 | 原文做法 | 本设计做法 | 理由 |
| --- | --- | --- | --- |
| 「配置目录即实验台账」 | 一句原则，寓于文件系统 | 承认双轨：仓库里有 YAML（可执行），系统里有 `配置台账`（可审计、可关联假设与实验记录） | 文件系统里的目录不能参与关联、过滤与告警；把它镜像进表之后，「哪些实验没有配置」才成为可筛选的清单。代价是存在两份，故 P1 加一致性校验 |
| 「事后记录实际环境」 | 写进日志头部即完成 | 额外在 `12 环境指纹` 建一行，并可关联回配置 | 日志是流水，表是账本。三个月后查漂移时，按 GPU 型号分组比在几百个日志文件里 grep 快得多 |
| 「不走极端，分层管理」 | 一段定性建议 | 落成 `是否主结果` 一个开关 + `未走完整锁定` 视图 | 把定性的「分层」变成可视的边界：不是错误清单，是提示——避免为了合规把预研实验也容器化 |
| 「自查脚本应随项目演进」 | 靠人记得往脚本里加检查 | `12 种子清单` 的 `是否可控 = 漏了` 与 `12 复现自查.失败说明` 两个字段承担「新坑」的登记 | 脚本的演进需要一个上游清单：坑先被记下来，才有机会变成脚本里的第 N 条检查 |
| 配置冻结 | 原文隐含「配置先于运行」即足够 | 默认用记录变更历史，主结果配置定稿后可用记录级写保护锁定（2026-10-19 落地） | 与第 10 讲预期结果卡同一条增强；锁定按需触发，不预先锁死——过早锁定会挡住正常的配置修订 |
