# 第 16 讲 调试方法论：系统落地设计

> 来源：`../design_principle/第16讲_调试方法论.pdf`
> 落地度：★★★★☆（高） ｜ 依赖：第 13 讲（AI 生成的代码是主要来源） ｜ 主体分期：P0
> 主产物：表 `16 调试记录`（一行 = 一次调试，五步法各占一段）+ 表 `16 断言清单`（一行 = 一处防御性断言）

## 1. 本讲方法要点

1. **AI 时代调试难，不在于缺陷更多，而在于缺陷伪装得更好**。三种错误模式：**错得更自信**（命名合理、注释肯定，错误被流畅的风格包裹）、**错在意图而非手误**（AI 实现的是一个「听起来差不多」的需求，方向错了细节越精致越难发现）、**错在接缝处**（多个函数分别看都对，拼起来语义对不上——单位不一致、索引约定不一致、空值约定不一致）。
2. **对策的出发点是「先重建理解，再开始排查」**：逐函数写下一句话的「它应该做什么」，再与实现对照，**分歧处往往就是缺陷的藏身地**。这个过程叫「认知回放」。
3. **一个读注释的技巧**：问「这段注释描述的是设计意图，还是仅仅在重复代码？」AI 倾向于写「这是什么」而不是「为什么这样做」，而「为什么」恰恰是你最需要的。如果注释给不出为什么，答案只能去契约与测试里找。
4. **科学调试五步法**（与科学方法同构，每步有退出标准）：
   - 稳定复现：把「偶尔会挂」变成「每次都挂」——固定种子、固定输入、记录触发条件。退出标准：**一条命令必然触发问题**。
   - 二分定位：在输入与报错之间对半切。退出标准：**定位到单个函数或单段逻辑**。
   - 最小用例：把可疑函数抽出来，用二三十行独立代码复现同样的问题。退出标准：**脱离项目后问题依然出现**。
   - 假设检验：对根因提出一个可证伪的假设，设计一个「若假设成立则应观察到某现象」的检查，**一次只验一个假设**。退出标准：**根因被证实，而非被猜测**。
   - 修复验证：三件事——最小用例变绿、完整流水线变绿、**补一个回归测试防复发**。退出标准：三样齐全。
5. **最常见的失败是在第二步尚未定位时就跳到第五步「改改看」**。没有定位的修复只是碰运气——改对了也不知道为什么对，下次换个形态还会再来。
6. **允许回退的搜索**：每步都要有「卡住就退回去」的预案。给每步设时间盒（稳定复现两小时做不出来，说明需要更系统的日志与监控；假设检验半小时没有新信息就该换假设）。
7. **向 AI 求助的输入三件套**：最小复现（而不是整个仓库）、预期与实际（明确写下「我期望输出是甲，实际输出是乙」）、已排除项（避免 AI 原地重复你的劳动）。**对输出的要求也要改：让 AI 列假设而不是直接给修复**——「给出三个最可能的根因，以及每个根因的验证方法」，然后由你逐个做实验确认。
8. **修复动作最好由你执行**：调试的价值一半在修复，**另一半在你对系统理解的更新，后者不能外包**。
9. **把调试过程本身记下来**：在哪个假设上浪费了时间、哪条线索最先指向真相。积累起来就是个人的「调试模式手册」。
10. **防御性断言三个必放位置**：函数入口（形状、类型、取值范围、单位——把契约的第一行变成可执行的检查）、数据管线节点（清洗后行数是否合理、关键字段是否仍有缺失、分布是否漂移）、训练循环关键点（输入有无 NaN、损失是否有限、梯度是否异常）。
11. **断言两条规范**：断言信息必须带上上下文（实际值与期望值），否则报错等于没报；断言检查的是**不变量**，不是业务分支——不要用断言替代正常的错误处理。
12. **断言位置的优先原则**：放在「假设最强、验证最少」的地方——函数入口的契约是最强假设，管线中间的不变量是最少验证的假设。
13. **对 AI 代码，断言的意义更大**：AI 不会提醒你「我这里做了假设」，它只会把假设埋进实现里；主动补断言等于把 AI 隐藏的设计决策暴露到明面上，**让自己重新拿回知情权**。
14. **断言的成本**：一个函数里不超过三条，三条都挑最关键的契约或不变量；超出三条，说明这个函数的职责可能本来就不够单一——这也是一个值得重构的信号。

**不建议系统化的部分**：

- **「认知回放」这个脑内过程不进系统**。它是一次性、不可观测的思考，系统只在 `错误模式` 字段里保留它的结论。
- **调试的具体命令与输出**。系统收「验证命令」与「验证结果」，不收整屏日志——日志留在终端与 CI 里。
- **时间盒的执行**。原文的「两小时 / 半小时」是防止把整个下午埋进同一死胡同的提醒；系统只登记耗时，不做强制中断（P1 可加巡检提醒）。
- **最小复现代码本体**。系统存它的 Word 数（是否 ≤ 30 行）与「脱离项目仍出现」的确认，代码本体留在仓库的 `debug/` 或粘贴在记录里由人决定。

## 3. 数据模型设计

### 3.1 表结构

空间：`科研方法`。表：`16 调试记录`（一行 = 一次调试）。

| 字段 | 类型 | 选项 / 说明 |
| --- | --- | --- |
| 编号 | 自动编号（前缀 `dbg-`） | —— |
| 问题标题 | 文本（标题字段） | 写成症状，如「训练到一半 loss 变 NaN」 |
| 五步·稳定复现 | 多行文本 | 触发命令与触发条件 |
| 必现 | 单选 | 一条命令必现 / 偶发 / 未稳定——对应第一步的退出标准 |
| 五步·二分定位 | 多行文本 | 切到哪一步、定位到哪个函数或逻辑段 |
| 定位结果 | 文本 | 到哪个函数为止——对应第二步的退出标准 |
| 五步·最小用例 | 多行文本 | ≤ 30 行；或在 `最小用例位置` 里给路径 |

| 脱离项目仍出现 | 复选框 | 对应第三步的退出标准 |
| 五步·假设检验 | `根因假设`（多行）／`验证方法`（多行：若假设成立应观察到什么）／`验证结果`（单选：证实/否定/部分） | 一次只验一个假设 |

| 耗时（小时） | 数字 | 与「时间盒」对照 |
| 浪费的假设 | 多行文本 | 在哪个假设上白花了时间——**它同时喂养第 15 讲的复盘与第 24 讲的品味曲线** |
| 错误模式 | 单选 | AI 意图误解 / AI 接缝不一致 / 自身的笔误 / 环境问题 / 依赖升级 |
| 关联契约 | 关联 → `13 接口契约`（单值） | 出问题的代码出自哪份契约 |
| 关联运行 | 关联 → `实验记录`（多值） | 失败或异常的那几次运行 |
| 审定三件套 | 单选 + 成员 + 时间 | 审定状态 / 审定人 / 审定时间 |

| 字段 | 类型 | 选项 / 说明 |

| 位置类型 | 单选 | 函数入口 / 数据管线节点 / 训练循环关键点 |

| 已添加 | 复选框 | —— |
| 拦截的缺陷 | 关联 → `16 调试记录`（多值） | 这条断言曾经拦下过什么——断言的战果 |
| 添加人 | 成员 | —— |
| 日期 | 日期 | —— |

**关系与公式**：

- `13 接口契约` → `16 调试记录` → `16 断言清单`：契约是实现的上游，调试是缺陷的下游，断言是把下游教训固化回上游的装置。
- `实验记录.结论方向 = 失败` → `16 调试记录.关联运行`：失败运行是调试记录的入口。
- **不使用跨表聚合**：`断言战果` 视图按 `拦截的缺陷` 的关联数排序（关联数量排序，不是公式）。

### 3.2 记录样例

**样例 1（`16 调试记录` 的一行——五步齐全，最后发现是接缝问题）**

| 编号 / 问题标题 | dbg-007 ／ 训练到 2k step 后 loss 变 NaN（复现率约 1/6） |
| 五步·稳定复现 | `python train.py --config exp-021.yaml --seed 7 --limit 2500 --debug_dataloader`；把 worker 数从 8 降到 1 后**必现** |
| 必现 | 一条命令必现（降 worker 后） |
| 五步·二分定位 | 注释掉后半个 epoch 的增强逻辑后不再出现 → 定位到 `src/data.py` 的 `_augment_batch` |
| 定位结果 | `_augment_batch`（单一函数） |
| 五步·最小用例 | 18 行：构造一个含 NaN 的 batch，跑 `_augment_batch`；`最小用例位置 = debug/dbg-007_repro.py` |
| 脱离项目仍出现 | ✅ |
| 根因假设 | 增强里的 `normalize` 把 0 方差列除以 0，产生 NaN；worker > 1 时该列在某分片里恰好全相等 |
| 验证方法 | 若假设成立：给该列加一个非零方差样本后 NaN 消失；且用 `nan` 计数器检查应在 `_augment_batch` 内首次出现 |

| 回归测试已补 / 提交号 / 验证命令 | ✅ ／ `c4e19a7` ／ `pytest tests/test_data.py::test_zero_variance_column -q` |

| 浪费的假设 | 「是不是 bf16 精度问题」——在这个方向上花了一小时，后来发现与精度无关 |
| 错误模式 | AI 接缝不一致 |
| 关联契约 | if-004（`split_by_time` 同一模块，但问题在 `_augment_batch`） |

## 5. 自动化设计

| 名称 | 触发器 | 条件 | 动作 | 防的坑 |
| --- | --- | --- | --- | --- |
| 修复须留痕 | `field_equals`（`验证结果` = 证实） | `回归测试已补` 未勾选 | `add_comment`（“跑通就收工不算完：补回归测试，并在提交信息里记录根因与验证方法”） | 「改改看居然好了」，下次换个马甲回来 |
| 同一问题复发检测 | `record_created` on `16 调试记录` | —— | `run_agent`（在历史记录里检索相似标题与根因，若命中则在评论里给出旧记录编号） | **同一个缺陷三个月后会换个马甲回来** |
| 未定位就修复即提醒 | `field_equals`（`验证结果` = 证实） | `定位结果` 为空 | `add_comment`（“没有定位的修复只是碰运气——改对了也不知道为什么对；请先补齐二分定位的结论”） | 第三步没走完就跳到第五步「改改看」 |

> 自动化的四条动作边界（动作只作用于触发记录、动作之间无分支、`notify` 须指定接收人、`field_equals` 会重复命中）见 `README.md` §3 与 `_系统能力现状.md` §2。

## 6. 智能体设计

### 站内智能体

**`调试助手`（模式：`prompt`）**

- 输入（用户提供）：三件套——最小复现（≤ 30 行）、预期与实际（明确写出「期望甲、实际乙」）、已排除项。
- 输出：**三个最可能的根因 + 每个根因的验证方法**；不直接给修复代码。
- 系统提示词骨架：

```text
你是调试助手。我会给你三样东西：最小复现代码、预期与实际输出的对比、我已经排除的假设。

【任务】给出三个最可能的根因，按可能性排序。对每一个根因：
1. 用一句话说明它为什么能解释「实际」而不是「预期」的现象；
2. 给出一个验证方法——「若此根因成立，则应观察到 X」的检查步骤；
3. 标出这个根因与我已经排除的假设是否冲突。

【硬约束】
- 不要直接给修复代码。修复动作由我执行；
- 我的「已排除项」里出现过的方向不允许重复提出；
- 如果三个根因都无法解释现象，直接说「信息不足」，并指出还需要什么观察数据；
- 不要写「检查你的代码逻辑」这类没有动作的泛泛之谈。
```

### 外部 MCP 工作流

1. **最小复现再缩减**：把已抽出的用例喂给 AI，问「能否再砍一半？」——更小的用例意味着更清晰的信号，也意味着贴给他人求助时对方愿意看完的概率更高（这一步由人发起，不自动执行）。
2. **断言缺口扫描（P1）**：外部 Agent 扫描仓库，找出「函数入口无断言且属 AI 生成」的位置，与 `16 断言清单` 比对，输出待加断言的清单。
3. **错误模式回流到契约**：从 `16 调试记录` 拉「AI 意图误解」类的记录，按 `关联契约` 分组，生成契约修订建议清单（人工发起）。

### 红线（AI 只能给草稿）

- **修复动作由人执行**。调试的价值一半在修复，另一半在你对系统理解的更新，后者不能外包。
- **`根因` 必须被证实而非被猜测**。`验证结果` 由人填，且必须能指向 `验证方法` 里那次具体的检查。
- **认知回放由人做**。逐函数写「它应该做什么」再与实现对照，这个过程不可外包。
- **`浪费的假设` 由人诚实填写**。它是最有价值的字段之一，也最容易被美化。

## 7. 与其他讲的接口

- **上游**：`13 接口契约`（AI 生成的代码是主要来源）；`实验记录`（`结论方向 = 失败` 的运行引出调试）。
- **下游**：
  - 第 13 讲：错误模式反过来改契约写法——契约的三个自检中「无模糊措辞」这一条的主要经验来自本讲。
  - 第 15 讲：`浪费的假设` 与错误模式进 AI 复盘与周复盘。
  - 第 22 讲：合规与统计区不涵盖调试，此处不交叉（原文未要求）。
  - 第 24 讲：`浪费的假设` 的长期分布喂养品味曲线（哪些直觉反复失效）。

## 8. 分期实施与验收

### P0（纯配置，零代码）

1. 建 `16 调试记录`（自动编号 `dbg-`）与 `16 断言清单`。
2. 建视图：未定位 / 无回归测试 / 错误模式分布 / 接缝类缺陷 / 浪费的假设 / 待加断言 / 断言战果 / 断言规范缺口。
3. 建两个表单视图：`开一条调试记录`、`补修复`。
4. 建三条自动化：修复须留痕 / 同一问题复发检测 / 未定位就修复即提醒。
5. 建站内智能体 `调试助手`，提示词入 `提示词库`。
6. 打通接口：`关联契约` → `13 接口契约`；`关联运行` → `实验记录`。

### P1（少量增强）

| 需求 | 说明 | 建议落点 |
| --- | --- | --- |
| 断言缺口扫描 | 扫描仓库找「入口无断言」的位置 | 脚本 / MCP |
| 时间盒巡检 | 记录停留超过 2 小时且 `定位结果` 仍为空时提醒 | `schedule` + `run_agent` 巡检 `16 调试记录` |
| 错误模式回流到契约 | 按契约分组统计错误模式，生成契约修订建议 | MCP 工作流 |
| 「已排除项」独立成表或字段 | 现在要写在 `五步·假设检验` 里 | 新增多选/多行字段 |

### P2（可选）

- 调试模式手册：按 `错误模式` + `问题标题` 的关键词索引历史记录，形成可检索的个人手册（原文第 16.3 节提到的「调试模式手册」）。
- 断言战果的季度报告：哪几条断言最划得来——它是「断言写在哪」的经验沉淀。

### 验收标准

1. `无回归测试` 视图为空：每条被证实的根因都有回归测试与提交号。
2. `未定位` 视图里的每一条都没有进入修复阶段（`验证结果` 为空）。
3. `错误模式分布` 视图里 `AI 接缝不一致` 与 `AI 意图误解` 两类有记录——它们是第 13 讲契约改进的原料。
4. `16 断言清单` 里三个位置类型各至少有一条 `已添加`。
5. 抽查一条历史调试记录：五步的退出标准都能对上（必现 / 定位到单个函数 / 脱离项目仍出现 / 根因被证实 / 三样齐全）。
6. `浪费的假设` 字段在多数记录里非空——**它证明调试过程被复盘过，而不只是被走过**。

## 9. 与原文的偏差说明

| 偏差 | 原文做法 | 本设计做法 | 理由 |
| --- | --- | --- | --- |
| 五步法 | 一套方法论，步骤与退出标准写在文里 | 拆成字段组，并把每一步的退出标准落成一个可判的字段（`必现` / `定位结果` / `脱离项目仍出现` / `验证结果` / `回归测试已补`） | 退出标准如果不能被检查，五步法就会退化成「凭感觉走到第三步」；每一处「退出标准」都对应一个字段，是这个设计的主要增量 |
| 「浪费的假设」 | 一句提醒（在哪个假设上浪费了时间） | 独立字段，并建 `浪费的假设` 视图 | 原文的思考题第 1 问（「根因未明下次会在什么场景复发」）要求可回顾；做成字段才能按错误模式统计 |
| 防御性断言 | 三个位置 + 两条规范 | 表 `16 断言清单`，一行一处，含 `拦截的缺陷` 关联 | 断言的价值在于「拦下了什么」——把战果记下来，下一处该加断言的地方就不再是猜的 |
| 「三条断言上限」 | 经验比例 | 不做强校验，只在文档中说明 | 把它做成硬校验会挡住合理的四断言函数；原文自己也说「超出三条是重构信号」，即它是一种提示而非规则 |
| 同一问题复发检测 | 「同一个缺陷三个月后会换个马甲回来」 | `record_created` 触发 `run_agent` 检索历史相似记录 | 原文只有提醒，没有动作；检索历史记录正是 AI 擅长的事——这是本讲唯一一处用 AI 补人工记忆的地方 |
| 时间盒 | 两小时 / 半小时的硬提醒 | P0 只记耗时，P1 加巡检提醒 | 时间盒的判据依赖对问题类型的直觉，统一阈值会误伤；先积累耗时数据再定阈值 |
