# 《AI 时代的科研方法》系统落地设计文档

> 来源：《AI 时代的科研方法》24 讲（`../design_principle/第01讲…第24讲`）。
> 本目录回答一个问题：**这本方法书里的哪些部分，可以直接做进现有系统**——用什么表、什么视图、什么自动化、什么智能体承载，配合哪些外部脚本与 MCP 工作流。
> 核对时间：2026-10-18。

## 1. 这套文档是什么

一套 24 篇的落地设计文档，一讲一篇，外加三份公共文件：

| 文件 | 作用 |
| --- | --- |
| `_系统能力现状.md` | 设计底座。所有「可落地」判断以它列出的能力为准；未列出的能力一律视为不存在。 |
| `_各讲落地要点.md` | 设计契约。表名、字段、视图、自动化、接口、分期在这里定死，各讲文档只做展开。 |
| `_文档模板.md` | 每讲文档的写作模板（九个固定小节）。 |
| `README.md` | 本文件：索引、规约、路线图、怎么用。 |
| `第01讲…第24讲` 各 `.md` | 单讲设计文档。 |

## 2. 目标与形态

**目标**：把一本方法论读物的 24 讲，落成一个**可以真的用起来的科研工作台**，而不是 24 篇读后感。

**形态**：一个 base（空间），名为 `科研方法`。全部内容装在其中：

- 表名前缀 `01 `…`24 ` 对应讲次；跨讲共享表不加前缀（共 12 张；另有 `10 预期结果卡` 带讲次前缀，与 `10 实验矩阵` 成对使用）。
- 每讲配 1–4 张私有表、若干视图、若干自动化、按需配智能体。
- 图表、Lint 脚本、训练代码等**留在系统外**，系统只承载台账、清单与留痕。

**为什么是一个 base 而不是 24 个**：全书的方法是一条证据链——`决策 → 假设 → 配置 → 实验 → 图表 → 段落 → 核查 → 复盘`。链上的每一环都要能指回上一环。跨 base 会让关联字段失效，证据链就在最该硬的地方断掉。

## 3. 复用能力摘要

系统已具备、且本设计大量依赖的能力（完整清单见 `_系统能力现状.md`）：

- **字段**：28 种，含自动编号（可做 `H-` / `exp-` / `ck-` 业务编号）、关联与双向关联、查找引用、公式（同行字段算术与比较 + 跨表聚合 `TABLEROWS` / `TABLESUM` / `TABLECOUNT`）、文本类字段唯一值约束（DOI 查重）、按钮（改字段值 / 打开链接 / 写评论 / 锁定记录）。
- **视图**：grid 表格、kanban 看板、calendar 日历、gallery 画册、form 表单、gantt 甘特；过滤器 11 种操作符（比较值支持 `today` / `week_start` / `month_end` 等相对日期）、排序、分组（≤3 层）、隐藏字段、行高、颜色规则（同样支持相对日期）、日期字段绑定、甘特依赖与进度字段、视图保护。
- **记录**：评论、变更历史（`list_record_history`）、关注、单记录分享、记录详情页布局（单栏/多栏/分组，1–3 列）、记录级写保护（`lock_record` / `unlock_record`，锁定后不可改不可删、解锁留痕）。
- **自动化**：6 类触发器（`record_created` / `record_updated` / `field_equals` / `button` / `webhook` / `schedule`）× 9 类动作（`set_field` / `create_record` / `add_comment` / `notify` / `http_request` / `send_email` / `feishu_bot` / `feishu_digest` / `run_agent`），带运行记录与手动试跑；动作取值与条件比较值支持 `today+N` / `today-N` / `week_start` 等相对日期，`create_record` 可用 `tableId` 指定同库目标表并做 `{字段名}` 插值。
- **文档**：文件夹、内置模板 10 个（实验前思考 / 实验后复盘 / 研究笔记 / 可行性速报 / 放弃备忘录 / 分类学说明 / 论文初稿 / 披露声明 / Cover Letter / 回应信）、文档 ↔ 记录挂靠（带 label）、历史版本自动归档与回滚、Markdown 渲染。
- **智能体**：站内 LLM 智能体，`tools`（多轮工具调用）/ `prompt`（单次生成）两种模式，6 个工具（`list_tables` / `get_table_schema` / `query_records` / `create_record` / `update_record` / `add_comment`），按触发者身份鉴权，带逐步运行日志。
- **MCP**：stdio 版与 HTTP 版（`/api/mcp/tools`），约 120 个工具，`dwa_` 令牌按空间授权（owner / editor / viewer）。
- **仪表盘**：bar / pie / count / line / donut 五种图表 + 切片器。
- **其他**：CSV 导入导出、空间级 Zip 导出、ICS 日历订阅、备份恢复、使用度量。

**能力边界（设计时反复撞到的四条）**

1. cron 已支持到**月 / 季 / 年**级（2026-10-19 起）：`every:N` / `hourly` / `N` / `daily:HH:MM` / `weekly:D:HH:MM` / `monthly:DD:HH:MM` / `quarterly:M-D:HH:MM` / `yearly:M-D:HH:MM` / `m h * * *`。月复盘、学期复盘与年度回顾的自动提醒可直接配置。
2. 自动化动作里**没有「批量查询记录」**。凡「巡检一批记录再逐条处理」的需求，走 `schedule + run_agent` 或 `http_request`。
3. 算式能力：同行字段的算术与比较已可用（2026-10-19），跨表只有行数类聚合。**分母来自别条记录的比值（通过率、完整率、新增率）交给仪表盘或脚本，不在表内算**。
4. 已下线前端入口的能力（工作流审批、ACL、公开分享、通知中心、跨表同步）必须注明配置途径为 **MCP / REST**，本设计中不依赖它们。

另有三条自动化自身的约束（源码核对，`src/store.ts`），会直接决定设计长什么样：

- **动作多数只能作用在触发记录上**：`set_field` 改不了别的记录（但取值可用 `today+N` 等相对日期）；`create_record` 默认建在触发器绑定的表，也可用 `tableId` 指定同一库内的另一张表；跨库建档才需要走 `run_agent` 或人工补录。
- **动作之间没有条件分支**，也不读取上一动作的输出：推送只发固定文案，数字与清单在表内看。
- **`field_equals` 是「当前值等于」而非「值刚变为」**：字段保持该值期间每次更新都会重新命中，只配提醒类动作。`schedule` 触发的自动化以绑定表第一条记录为上下文（`run_agent` / `feishu_digest` 例外），表内无记录时会被整条跳过。
- `record_updated` / `field_equals` 触发器与 `create_record` / `notify` 动作**不在前端编辑器里**，需经 MCP / REST 配置——仍算 P0。

## 4. 统一规约

### 4.1 命名与编号

- 表名：`NN 中文名`（如 `15 实验记录`）；共享表用不带前缀的短名（如 `文献库`）。
- 视图名：用中文短语描述意图，不用「视图 1」这类名字（如 `空格清单`、`严谨性缺口`）。
- 编号字段一律用系统「自动编号」生成，前缀在字段里配置：`H-` 假设、`exp-` 配置、`ab-` 消融变体、`ck-` 核查项、`rv-` 审稿意见、`D-` 决策、`G-` 空白假设、`ref-` 引用核验、`ai-` AI 使用日志。

### 4.2 单一事实来源

每篇文档的第 7 节都要写明「本讲产物只在哪个表/哪篇文档维护」。跨表引用一律用**关联字段**，不复制文本。这条规约是「关键证据不能事后涂改」的前提：如果同一个事实有两份副本，就有一份可以被悄悄改掉。

### 4.3 AI 产出的流转（红线 2 的落地）

**任何 AI 写入的字段，其所在表必须有 `审定状态（单选: 待审定/已审定/退回）`、`审定人`、`审定时间` 三个字段。**

三类 AI 产出一律先落草稿：

| 类型 | 落点 | 人工核验动作 |
| --- | --- | --- |
| AI 对某条记录的意见 | 记录评论 | 人读后决定是否改字段 |
| AI 生成的字段内容 | 草稿字段 + `审定状态 = 待审定` | 人核验后改状态、写审定人 |
| AI 产出的成段文字 | 文档草稿或段落卡 `AI 初稿待核` | 逐句核查，数字回原文 |

**明确禁止 AI 代劳的三处**：`文献库.局限`（必须手写）、`核查清单.结果`（不能用 AI 判通过/不通过）、引用核验的结论。

### 4.4 留痕

- 系统字段「创建时间 / 创建人 / 修改时间」+ 记录变更历史，天然提供「不可事后涂改」的证据。
- 需要更强防篡改的地方（如预期结果卡锁定、核查清单冻结）用**记录级写保护**（`lock_record`，2026-10-19 已落地）：锁定后不可改不可删、解锁留痕。
- 关键状态变更（证伪、放弃、冻结）必须配一条 `add_comment` 留痕，不做静默 set_field。

### 4.5 视图组织

每讲至少两个视图：一个**浏览视图**（分组/看板，日常用），一个**闸门视图**（筛选出「不该存在的东西」，如空字段、缺项、红线项）。闸门视图的意义是把纪律变成可看见的清单——它们长期为空，说明纪律在起作用。

计数口径：「视图 N 个」只计表格 / 看板 / 日历 / 画册 / 甘特五类，表单视图（录入入口）单独列出、不计入；自动化按触发器绑定的表计，同一条规则配在两张表上算两条；智能体含可选项，复用别讲的智能体不重复计。

### 4.6 分期

| 分期 | 含义 | 判据 |
| --- | --- | --- |
| **P0** | 纯配置，零代码，今天就能建 | 只用到现有字段类型、视图、自动化、智能体；含经 MCP / REST 配置的触发器与动作（前端编辑器未列出的那四类仍算 P0） |
| **P1** | 少量增强 | 需要新增能力，文档写明建议落点文件 |
| **P2** | 可选 | 好用但不必要，投入产出比低于 P1 |

### 落地度评定标准

**落地度衡量「这一讲的方法有多少比例能被系统承载」，不是衡量这一讲的重要性。**

| 评级 | 含义 | 典型特征 |
| --- | --- | --- |
| ★★★★★ | 几乎全部可落地 | 方法本身就是「结构化记录 + 定期检查」，系统能承载 80% 以上 |
| ★★★★☆ | 主体可落地，但有一块在系统外 | 涉及代码、脚本、检索执行、绘图本体等系统不托管的部分 |
| ★★★☆☆ | 只有一小部分该系统化 | 核心是人的判断、习惯或长期坚持，系统化反而有害 |

第 24 讲评为 ★★★☆☆ 是**刻意的**：长期主义的核心是十年的坚持，不是十年的表格。把纲领与能力曲线做成表是为了让年度回顾有据可查，不是为了把坚持变成打卡。

## 6. 分族导航

全书 24 讲可以按证据链分成六族，族内讲次互相喂数据：

**族一 · 选题（01–04）**：从模糊主题到可行选题。`问题矩阵 → 差异假设 → 可行性冲刺 → 决策日志`。
主问题：**做什么**。族内出口是一条「存活假设」和一个带时间戳的判断记录。

**族二 · 文献（05–08）**：检索、阅读、综述、知识库。四讲的产物都指向同一张 `文献库`。
主问题：**别人做过什么、我读到了什么**。族内出口是一张填满的对照表与一页主题索引。

**族三 · 假设与实验（09–12）**：假设、实验矩阵、消融、可复现。`假设登记` 是这一族的轴。
主问题：**怎么验证**。族内出口是一组可复现、可解释、带机制的实验证据。

**族四 · 代码与数据（13–16）**：契约、数据版本化、实验追踪、调试。
主问题：**证据可不可信**。族内出口是六字段完整的运行档案与一份数据卡。

**族五 · 写作与投稿（17–22）**：写作流水线、图表、投稿、合规、回应、核查。
主问题：**怎么交付**。族内出口是一份通过五区二十五条的稿件。

**族六 · 系统与长期（23–24）**：把前缀二十二讲沉淀为系统与纲领。
主问题：**怎么让它持续运转、并且越跑越强**。

## 7. 分期路线图

- **第三批（实验与代码）**：第 09–16 讲的表、视图与自动化。
- **第四批（写作与投稿）**：第 17–22 讲的表、视图与自动化。
- **第五批（系统）**：`模板库`、复盘记录、年度回顾、纲领与能力曲线。

## 8. 怎么用这些文档

**给自己**：先读 `_系统能力现状.md` 确认边界，再读 `_各讲落地要点.md` 一次性建完 P0 的表。之后每讲的文档当施工图用——按第 3 节的表结构建表，按第 4 节配视图，按第 5 节配自动化。

**给 AI 助手**：把 `_系统能力现状.md` + 某一讲的文档一起给，AI 就能生成具体的建表/建视图/建自动化步骤。文档里所有表名、字段名、选项值都是精确的，可直接照抄。

**给 MCP Agent（外部 Agent）**：Agent 通过 `dwa_` 令牌连同一个库，可以批量建表、批量导入文献、批量核验 DOI、把 CSV 结果写进 `实验记录`。注意：工作流审批、ACL、公开分享、通知中心、跨表同步这几项的前端入口已下线，需要配置时走 MCP / REST。

**一条使用建议**：不要试图一次把 24 讲全部建好。**先建骨架五表（`提示词库` / `01 问题矩阵` / `文献库` / `假设登记` / `实验记录`），用两周，再按真实痛点长出后面的表**。这套文档的价值不在于被完整实现，而在于当你想加一张表时，能立刻查到它该长什么样、跟谁关联、有哪些纪律要一起带上。
