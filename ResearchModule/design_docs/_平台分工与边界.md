# 平台分工与边界：记录层 · 资产层 · 执行层

> 本文件回答三个问题：**知行人生（本系统）做到哪为止？Zotero 等专业工具接走什么？还需要引入哪些平台？**
> 依据：`../design_principle/` 24 讲原文、本目录 24 篇落地设计、`_系统能力现状.md`（核对时间：2026-10-20）。

## 0. 结论先行

三条判断的对照结论：

| 判断 | 结论 | 需要修正的地方 |
| --- | --- | --- |
| ① 知行人生只做记录 | 成立，但「记录」要精确定义为**登记 + 约束 + 对账**，不是被动存档 | `文献库` 把资产（PDF/元数据）与记录（判决/卡片）混装在一张表，是当前最大越界点 |
| ② Zotero 做文献管理、关联、阅读、问答 | 管理、阅读、**单篇问答**归 Zotero；**关联与跨条目问答必须分层** | 四类关系（上承/冲突/共享假设/部件复用）是带审定的判断记录，留在本系统；否则第 07/08/22 讲的证据链断裂 |
| ③ 是否引入其他平台 | 需要，但按「痛点驱动」纪律建**最小集**：本系统 + 四个必备外部平台 + 四类条件引入（投稿系统只需登记），明确不建议通用笔记库 | 见第 2 节 |

一句话原则：**资产跟着专业工具走，判断跟着记录系统走；两边用稳定键对接。**

依据来自第 24 讲：工具会换代——「把工作流建立在原则（清单、记录、核查）而非具体工具上的人，换代成本是一个下午」；反过来，把资产焊死在记录表里的人，每次换工具都要重抄一遍台账。

## 1. 三层分工模型

### 1.1 定义

- **资产层**：文件与元数据本体。文献（Zotero）、代码与配置（Git 仓库）、数据（文件系统 / DVC / 对象存储）、正文与图表源文件（写作与绘图环境）、训练日志（追踪平台）。
- **执行层**：产生新信息的动作。检索、阅读、AI 生成、跑实验、画图、写作。
- **记录层**（本系统）：判断、承诺、核验、留痕。决策、假设、预期、判决、关系、核验、复盘、模板。

### 1.2 三条判据（一个字段/一张表该进哪层）

1. 它是**你做的判断**，还是**工具产出的物**？物 → 资产层；判断 → 记录层。
2. 它是否需要**留痕 / 冻结 / 对账**？需要 → 记录层。
3. 如果明天换掉 Zotero 或追踪平台，它是否**应该存活**？应存活 → 记录层（用键引用资产）；不该 → 资产层。

### 1.3 「记录平台」的精确定义

记录 = **登记**（结构化字段）+ **约束**（状态机、闸门视图、写保护、AI 草稿隔离）+ **对账**（编号引用、`check_config_ledger` 这类一致性检查）。

- 含约束与对账才算记录平台；不含就退化为一张网盘表格。
- 不含执行、不存资产本体。这两条是边界，不是缺陷。

### 1.4 三种越界形态（反例）

- **资产进记录层**：把 PDF 存进 base——双份维护，且 base 无全文索引，存了也检索不了。
- **执行进记录层**：让站内智能体扛预读、聚类、红队的主力——模型能力与上下文都吃亏（详见 4.3）。
- **记录焊死在工具上**：把论文正文 TeX 只存在某一工具界面里——换代即迁移，违背第 24 讲纪律。

### 2.2 按痛点引入（先过三问闸门）

| 平台 | 触发条件（痛点） | base 里保留什么 |
| --- | --- | --- |
| 实验追踪平台（WandB / MLflow / TensorBoard） | 手工登记开始漏字段；多人互看不到；需要跨项目对比 | 审计行：`run-id` + 六字段快照（六字段以平台为准） |
| 数据版本工具（DVC / git-lfs / 对象存储） | 数据体量或版本数超出 git 适用范围 | `14 数据资产` 数据卡（哈希 / 许可 / 可否重建） |
| 协作写作环境（Overleaf / Word / Google Docs） | 出现合作者、投稿要求 Word | `17 段落卡` + `18 图表台账` + `核查清单` |
| 引文网络 / 检索增强工具（Semantic Scholar API、Connected Papers 一类） | 滚雪球靠手工已吃力（设计现有路径是脚本调 Semantic Scholar API，见第 05 讲） | `05 检索日志` |

**三问闸门**（第 23 讲的三问，从「模板」推广到「平台」）：它防的坑我**实际踩过**吗？它与 base 的**哪个键/哪个例程**接口？我承诺在**哪个复盘**里维护它？三问答不出 → 不加。

### 2.3 不建议引入

- **通用笔记 / 第二大脑（Obsidian / Notion / Logseq）**：主题索引与四类关系的家已定在本系统（带审定与证据链），再引入一个就是第二个事实来源；第 08 讲明确反对目录完美主义与工具链过重。若已在使用，只当草稿区，**单向流入**，不作来源。
- **AI 阅读工具（SciSpace / ChatPDF 类）作为第二文献库**：问答可以用，但元数据与条目不得沉淀在那边——沉淀即双源。
- **Compliance note**：第 20 讲「审稿人不得将评审稿件上传至公开 AI 服务」的红线同样约束 Zotero 的云端 AI 插件。未发表稿件与评审材料只用本机 / 自托管模型，或先脱敏（与第 15 / 23 讲的脱敏纪律一致）。

## 4. 对现有设计的修正点（批判清单）

### 4.1 `文献库` 把资产与过程混装（优先级最高）

- **现状**：29 个字段同装一张表（线上已建口径）。`PDF`（附件）与 `标题/作者/年份/发表处/链接`（资产元数据）跟 `阅读级别/淘汰理由/五元组`（过程判断）混在一起。
- **问题**：① 与 Zotero 双写，元数据与 PDF 出现两个家——违反设计自己要遵守的「单一事实来源」红线（`README.md` §4.2）；② base 无 PDF 全文索引，附件存了也搜不了；③ 元数据手抄是纯消耗，且会静默漂移。
- **建议**：字段分三层（仍是一张表，用记录详情页分组区分）：
  - **键层**：`DOI`（已有，唯一）、`Zotero 键`（新增，文本，唯一）——两系统接口；
  - **快照层**（脚本同步、人工只读）：`标题 / 作者 / 年份 / 发表处 / 链接`；脚本就绪前允许手抄，标注「临时」；
  - **记录层**（人写，是本表的真正价值）：其余 22 个字段全部保留。
  - `PDF` 字段：**建议删除**。文件本体在 Zotero（本地数据目录），担心丢失是备份问题（备份 `zotero.sqlite` + `storage/`），不是往 base 再存一份的理由。特殊情形（如冻结投稿时引用的原件）用 `22 讲核查附件` 承载。

### 4.2 Zotero 接口的优先级：P2 → P1

- 现状：第 06 讲把「与 Zotero / Better BibTeX 双向导出」列为 P2、可选。
- 问题：这条接口是**防止双录的关键路径**，把它排到可选，等于默认长期手工搬运；而第 15 讲的纪律恰恰是「秩序先于工具、不折腾不欠账」。
- 建议（P1，按序做）：
  1. 采纳 4.1 的字段改造（`Zotero 键`）；
  2. Better BibTeX 导出（CSL-JSON / BBT JSON）→ 外部 Agent 经 MCP 批量建 `文献库` 草稿（`审定状态 = 待审定`，直接复用「幻觉隔离」自动化——AI 产出默认落草稿的红线自动生效）；
  3. 每周 30 分钟例程里顺带跑一次增量同步；
  4. 反向（base 四类关系 → Zotero 标签镜像）可选，P2。

### 4.3 站内智能体的定位：主力 → 巡检员

- 现状：31 个站内智能体承担预读出题（`预读出题机`）、魔鬼代言（`魔鬼代言人`）、红队审查（`红队审查员`）、聚类归纳（`聚类归纳员`）、回应信起草（`回应信起草员`）、Cover Letter 适配段（`适配段起草员`）等工作。
- 问题：这些是**实质性的 AI 执行**，对模型能力与上下文长度要求最高；站内智能体（6 个工具、基础 provider）恰是系统最弱的一环。把它们当主力，AI 产出质量会被最弱的管道限制。
- 建议：
  - **主力执行**放外部 AI（Claude / Cursor 等，经 MCP 读写 base）；`提示词库` 仍是 base 的资产——提示词的家不变；
  - **站内智能体保留「定时巡检员」角色**：`schedule + run_agent` 的逐条留言、汇总报数、模式检索（如第 15 讲 `每周复盘员`、第 16 讲「同一问题复发检测」自动化、第 22 讲 `清单看守员`），以及外部 AI 不在场时的兜底；
  - 要求只有一条：无论谁执行，产出**一律先落草稿**（`审定状态 = 待审定`），红线 2 不因换执行者而松动。

### 4.4 问答分层：单篇全文 vs 跨条目综合

前提②「Zotero 做问答」只对了一半，两种问法必须分开：

| 问法 | 家 | 为什么 |
| --- | --- | --- |
| 单篇 / 细节（「这篇的 loss 怎么定义」） | Zotero（全文 + 批注 + AI 插件） | 全文本就在那里；答案不进入证据链，不必落账 |
| 跨条目综合（「这些方法对噪声的共同盲区」） | base 条目 + 外部 AI | 第 08 讲的方法锚点：上下文来自**你亲手审定的条目**，不是训练记忆；结论按「复核记录」逐条回库核对 |

第 08 讲现在设计的 `跨条目提问机` 方向正确，只需把执行者换成外部 AI、结论经 `复核记录` 回挂。

### 4.5 四类资产的「家」要在文档里写死

现有设计有四处含糊，建议逐处钉死（否则必然长出第三份副本）：

| 资产 | 家 | base 只保留 |
| --- | --- | --- |
| PDF 与批注 | Zotero | `Zotero 键` + 判决与卡片 |
| 代码 / 配置 / 脚本 | Git 仓库 | 契约、审查结论、`配置台账` 审计行 |
| 数据本体 | 文件系统 / DVC | `14 数据资产` 数据卡 |
| 论文正文本体 | 写作环境（LaTeX / Overleaf / Word） | `17 段落卡`、工序、图表台账、核查清单 |

### 4.6 维护成本上限（把第 08/15 讲的减法纪律前置）

- 全量 56 表 / 180 视图 / 85 自动化不可能被一个人坚持；**系统的价值以被坚持使用的时长计价**（第 15 讲）。
- 硬约束建议：每周维护 ≤ 30 分钟（`08 维护日志` 例程）；闸门视图长期为空才算纪律在起作用；新增平台过 §2.2 三问；连续三个月未触发的字段/表/平台删或停用。
- 当前正确节奏：骨架五表已上线（2026-10-20）→ 用两周 → 只补真实痛点碰到的表；其余 16 讲的表设计当「施工图库存」，不当「施工计划」。

## 5. 接口规范：三把钥匙 + 三条同步纪律

**三把钥匙**（base 引用资产的唯一方式，全部作唯一值或校验键）：

| 资产 | 键 | 用在 |
| --- | --- | --- |
| 文献 | `DOI` / `Zotero 键` | `文献库`、`引用核验`、`07 对照条目` |
| 代码与配置 | commit sha + 路径 | `配置台账`、`12 环境指纹`、`16 调试记录` |
| 数据 | 路径 + 哈希 | `14 数据资产`、`实验记录.数据版本` |
| 实验运行 | `run-id`（`run-` 编号） | `实验记录` → `17 段落卡` → `18 图表台账` |

**三条同步纪律**：

1. **单一事实来源**：资产跟工具、判断跟记录。每个事实只在家一边；另一边最多是快照。
2. **单向同步**：Zotero → base 只同步快照层（脚本写入）；base → Zotero 只做标签镜像（可选）。任何字段不允许双向。

3. **人写判断永不被脚本覆盖**：脚本只允许写快照字段与 `待审定` 草稿字段；`阅读级别`、`五元组`、`局限`、关系、核实结论一律人写（沿用第 06/20/22 讲既有红线）。

## 7. 验收（怎么知道分工被执行了）

1. 元数据零手抄：新文献的标题/作者/年份/发表处全部来自 Zotero 同步（或明确标注「临时手抄」）。
2. base 里**搜不到** PDF 全文、代码、数据集、正文 TeX 本体——它们只在资产层。
3. `文献库` 里每条精读都有人写的 `局限` 与四类关系；关系可反向查询（「谁与 X 冲突」一键可得）。
4. 论文里的每个数字能沿「`17 段落卡.关联运行` → `实验记录.运行编号`（`run-`）→ `实验记录.配置` → `配置台账`（`exp-`）→ `代码提交`」回溯到一条原始记录。
5. 每周维护 ≤ 30 分钟；`未核实项`、`事后调整过`、`红线警告` 等闸门视图长期接近空。
6. 任何一个平台被替换（Zotero → 下一个管理器、追踪平台换代）时，base 里的记录**一行都不用改**——只需重指向键。
