# 知行人生 · 产品复盘与优化清单

> 视角：资深产品经理复盘。日期：2026-10-09。
> 口径：线上实例（`47.122.123.1`）实测数据 + 服务器状态 + 仓库代码。所有结论都给证据，未实测的推断会标注。

---

## 0. 一句话结论

**缺的不是功能，是"接通 + 可信 + 可回滚"。**

能力面已经很宽（142 个 HTTP 接口、108 个 MCP 工具、37 张表、24k 行代码），但仍有三处**"界面上显示正常、实际上不通"**的洞：

1. 两条飞书自动化都在空转（没有 webhook，静默跳过），其中定时那条还会写"上次运行"，给出**虚假的成功信号**；
2. 事件型自动化（新建/更新触发）**没有任何运行记录**，发没发出去、失败没有，用户无从判断；
3. 外部 Agent 通道（ChatGPT 等）**从公网接不进来**：域名未备案被阿里云拦截，只有 IP 直连可用。

另外，上一轮前端精简后留下的"半下线"状态已经不小：**37 张表里 17 张 0 行**，对应的后端接口和实现都还在。

## 2. P0：先修三个"显示正常但实际不通"的洞

### 2.1 飞书通知在空转（最高优先级）

**证据链：**

- 两条自动化都挂在 `多模态文档检索 / 任务` 表上，动作分别是 `feishu_bot`（新建科研任务通知）与 `feishu_digest`（每日 09:00 摘要）。
- 线上 `base_settings` 四个空间**全部没有配置飞书 webhook**（`integrations_json` 里查不到 feishu 相关键），自动化动作自身也没带 `webhookUrl`。
- 代码行为：`feishu_bot` 找不到 webhook 时只打一行 `console.warn`（`src/store.ts:1958`）；`feishu_digest` 直接返回 `{sent:false}`（`src/store.ts:2119`）——两边都**不报错、不提示**。
- 而定时自动化**照样写 `last_run_at`**（`src/store.ts:2062`），所以界面上会显示"上次运行：今天 09:00"，**看起来完全正常**。

**影响：** 用户以为"任务到期会有飞书提醒"，实际上一条都没发出去；而且这个假象会一直持续，因为没有失败信号。

**修法（按顺序）：**

1. 在空间设置里配置飞书机器人 webhook（这是产品核心出口：真实工作流在飞书里）；
2. 无 webhook / 发送失败时，在自动化卡片上**显式标红**（"未配置通知渠道，不会发送"），而不是只写容器日志；
3. 自动化加"**发送测试消息**"按钮，配置后一键验证；
4. 让 `last_run_at` 只在**真正发送成功**后更新，避免虚假信号。

### 2.2 事件型自动化没有运行记录

**证据：** `runAutomations()`（`src/store.ts:1839`，负责 `record_created`/`record_updated`/`field_equals`）**不写 `last_run_at`**；只有 webhook、按钮、定时三条分支会写（`src/store.ts:2005` / `2031` / `2051` / `2062`）。也就是说线上那条"新建科研任务通知飞书"的 `last_run_at = 0` **既不能证明它跑过、也不能证明它没跑过**——数据是空的。

**影响：** 自动化最需要"可信"的地方恰好没有观测。用户无法回答"我的通知为什么没来"。

**修法：** 统一在 `runAutomations` 里落一条运行记录（触发时间、命中动作、每个动作的成功/失败/跳过原因），UI 上给"最近运行"列表；失败可重试。这张表同时能当后续"使用度量"用。

### 2.3 外部 Agent 接不进来（域名不可用）

**证据：**

- `mcp_agents` 里 ChatGPT 通道 10-05 创建，**`last_used_at` 为空**——一次都没成功用上；Cursor 通道正常（最近调用 10-09 19:52）。
- 实测：`http://task.zhaopeinan.com/api/health` → **403（阿里云未备案拦截页）**；`https://task.zhaopeinan.com/api/health` → **连接重置（curl 000）**；`http://47.122.123.1/api/health` → **200**。
- 成因：域名未备案，阿里云边缘按 Host / TLS SNI 拦截。`docs/dns-migration-zhaopeinan.md` 记录过 Cloudflare 隧道方案（验证通过），但 10-07 已整体回滚到 IP 直连。
- 副作用：容器里 `DUOWEI_COOKIE_SECURE=0`（因为只能走 HTTP），Cookie 无法加 Secure 标记。

**影响：** "用手机 / 用别的 Agent 访问"这条线一直是断的；ChatGPT 这类只能连 HTTPS 域名的客户端永远连不上。

**修法（三选一，按成本排序）：**

| 方案 | 成本 | 说明 |
|------|------|------|
| A. 复用已有的 Cloudflare Named Tunnel | 低 | 服务器上隧道与凭据都还在（`/etc/cloudflared/config.yml`、`a5f607be-…json`），当时验证过 8 个域名可用；建议**只给 API 挂一个域名**，不动主站。需先确认 10-07 回滚的真实原因（速度/稳定性），再决定是否只对 API 恢复 |
| B. 走 headscale（Tailscale 兼容） | 中 | 服务器上 headscale 已在跑；远程设备接入内网后访问服务，零公网暴露，最安全，但要求客户端能装 Tailscale |
| C. 非大陆节点做出口 / 给域名备案 | 高 | 香港/新加坡小机器反代，或走完整备案流程 |

**建议：** 先做 A 的"API 单域名"版本（影响面最小），失败再退 B。

## 3. P1：把"能用"变成"可信"

### 3.1 备份（现状不错，补三件事）

现状值得肯定：每日 02:00 自动、WebDAV 外送、连续成功。要补：

- **附件纳入备份**：现在只备份 `duowei.db*`，`data/uploads` 不在内（当前 4KB 空目录，风险为零，但附件功能一旦启用就是数据缺口）；
- **恢复演练**：把"从坚果云取回 + 还原 + 验证"写成脚本/文档，没验证过的备份不算备份；
- **保留策略**：现在只留 3 份（最多回滚 3 天），建议改 7 天 + 每月留 1 份的滚动策略；
- 清理 `/opt/duowei/data/` 下 11 个手工 tar.gz。

### 3.2 部署与回滚（当前最大的运维风险）

- `scripts/deploy-aliyun.sh` 今天为 `--remote-build`、`.dockerignore` 等问题反复调试过；Caddy 配置有 10 个手工 `.bak`，说明线上配置在"手改 + 备份"模式下漂移。
- 建议：**把 Caddy 配置纳入仓库**（`infra/` 或 `deploy/`），部署脚本负责渲染与 reload；
- 部署后自动冒烟：健康检查 + 关键接口 + 首页 200，任一失败自动回滚到上一个镜像 tag（现在镜像是 `duowei:latest`，建议改成带时间戳 tag 保留上一版）。

### 3.3 CI（成本极低，收益立竿见影）

仓库已有 `npm run typecheck` 与 `npm test`（`formula.test.ts`、`store.test.ts`），但**没有任何自动执行**（无 `.github/workflows`）。加一条 GitHub Actions（typecheck + test + build:web）即可，半小时的事。

### 3.4 健康与告警

服务本身没有任何监控：容器挂了、磁盘满了、证书过期了、备份失败了，都不会有人知道。建议每天推一条"值班日报"到飞书（正好复用 3.1 修好的 webhook）：容器状态、磁盘、最近备份结果、昨日写入量。

### 3.5 清理"半下线"状态（17 张空表 + 对应接口）

上一轮前端精简下线了工作流、跨表同步、公开分享、行列权限、记录关注、通知中心、应用模式，但后端接口、数据表、实现代码都保留着。当前状态下：

- 读者（人或 Agent）看到的接口面是 142 个，真实在用的远少于此；
- 未来任何改动都要考虑这 17 张表和一堆分支，维护成本随时间长。

**建议二选一：**

- **A（推荐）彻底删**：代码 + 表 + 文档一次性收干净，需要时从 git 历史里捞；
- **B 明确标注**：保持实现，但在 README / 上手指南 / MCP 工具描述里标注"未启用，默认通道"。

不要维持现状：既不是"支持"，也不是"不支持"。

## 4. P2：产品方向上的建议

### 4.1 深水区放在"个人科研工作流"，而不是继续对标飞书

飞书多维表格目录能力已经 `done*`，继续补 minor 能力边际收益很低。用户真实的链路是**任务 → 实验 → 文档 → 总结**，值得做深的是：

- **实验台账**：实验任务表 + 指标字段 + 视图看板（现在 24 条实验任务已经这么用了，但缺少指标聚合/对比）；
- **自动周报**：按周把三个空间的任务、实验、文档变更聚合成一篇周报（发飞书 / 存文档）；
- **文献—任务联动**：多模态文档检索空间已有"任务 + 维表"，可以补 arXiv/文献元数据字段与引用关系。

### 4.2 单用户假设下的减法

真实用户数 = 1。多人相关的能力（成员管理、权限、审批流、通知中心、分享）可以**整体冻结**；"给别人看"的需求收敛成"只读链接"一种形态就够。

### 4.3 数据出口（现在只能进，不能出）

只有 CSV 导出，没有整库/空间级导出。建议：空间级导出（JSON + Markdown + 附件打包）、文档导出 Markdown。数据在自己手里，才敢长期投入。

### 4.4 移动端

已有 `mobile.tsx` / `touchDrag.ts`，但入口只有 IP + HTTP。2.3 一旦解决（HTTPS 域名），手机可用性会明显上一个台阶（可加到主屏、Cookie 安全、部分浏览器才允许的 API）。

### 4.5 智能问答可插拔 LLM

`/api/assistant/query` 现在是服务端规则引擎。用户在自己部署模型，可以把它改成可插拔 LLM（本地推理优先，隐私不出机器），Agent 使用说明空间也能受益。

### 4.6 加一个轻量使用度量

现在做产品决策只能"翻数据库猜"（本次复盘就是这么干的）。建议一张按天聚合的小表：API 调用量、MCP 调用量、各表写入量、自动化触发/成功数。有了它，"哪些功能该删、哪些该做深"就不再靠拍脑袋。

---

## 5. 不建议做

- 付费能力、商业套餐（单用户工具）；
- 插件沙箱与安装包市场（`plugin_hooks` 0 行）；
- 对象存储 / CDN（附件目录 4KB，远端 CDN 无意义）；
- 继续按飞书目录逐条补 minor 能力（已 `done*`，边际收益低）。

## 6. 建议的执行顺序（两周）

**第 1 周（止血 + 可信）**

1. 配置飞书 webhook，两条自动化真正发出去；无配置时 UI 标红 + 测试按钮（P0-2.1）
2. 事件型自动化落运行记录（P0-2.2）
3. API 单域名经 Cloudflare 隧道恢复，或改用 headscale（P0-2.3）
4. 加 CI：typecheck + test + build（P1-3.3）
5. 备份：纳入 uploads + 保留 7 天 + 写恢复演练文档（P1-3.1）

**第 2 周（工程健康 + 收尾）**

6. 部署冒烟 + 镜像 tag 回滚 + Caddy 配置入仓（P1-3.2）
7. 每日值班日报推飞书（P1-3.4）
8. 清理 17 张空表与对应接口，或明确标注（P1-3.5）
9. 空间级导出（P2-4.3）
10. 使用度量落地（P2-4.6）

**衡量标准（两周后能回答）**

- 飞书通知：能在手机上收到新建任务通知与每日摘要，且失败能在界面上看到；
- 外部 Agent：ChatGPT（或任一 HTTPS 客户端）能用同一个 MCP 端点读写数据；
- 工程：任意一次改动有 CI 把关，部署失败能一键回滚；
- 产品：数据库里不再有"是支持、是废弃"说不清的表。
